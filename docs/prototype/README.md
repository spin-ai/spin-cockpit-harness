# 页面优化原型

可直接打开的静态原型（多数是改版方案，`entry-points.html` 是入口清单），用来说明「资料 / 记忆 / 人物 / 协作场景 / 一条 Mission 穿过四个页面」该长什么样。不是最终实现，但每个改动都对应一处具体问题。
打开方式：双击对应 HTML（无构建、无依赖）。右上 `◐` 切亮 / 暗。

| 文件 | 页面 | 主要解决的问题 |
|---|---|---|
| [`knowledge.html`](knowledge.html) | 资料（知识库） | 输入与输出被拆到两列；引用点不动；解析引擎配置占满右栏；看不到解析质量 |
| [`memory.html`](memory.html) | 记忆 | L1–L4 是内部词汇；复核队列被压在正文下；主 CTA 是「运行 Dream」；注入预览只读 |
| [`persona.html`](persona.html) | 人物（人物建模） | 只有陈述性事实，没有性格与处事；没有单一可读的人设卡；关系网与置信度缺位 |
| [`coordination-scene.html`](coordination-scene.html) | 场景（协作场景） | 场景不应只是一张执行配置表；多 Agent 协作需要拟人化舞台；办公室只是 Stage Pack 的一种 |
| [`warroom.html`](warroom.html) | 场景（作战室舞台） | 发布窗口的协作不是工位：长桌、主屏、GO / NO-GO 闸门和复盘墙才是值班的空间语言 |
| [`carrier.html`](carrier.html) | 场景（航母 · 电磁弹射） | 流水线把所有任务画成同一条传送带；航母是「多弹射位并发 + 单着舰道串行」，正好对上 worker 与 review 的真实结构 |
| [`motion-workbench.html`](motion-workbench.html) | 场景（动效工作台） | 舞台只演结果，不解释原因；动效只有三档、改完只能等下一次真实状态变化；关掉动效后看不看得懂没人验证 |
| [`bot.html`](bot.html) | Bot（会话与审计） | 主动开口的 bot 不能只有气泡：沉默 / 被频控 / 转人工要和「说过的话」平级可见；每条都要能展开「为什么说」。配置（人设 / 执行体 / 日程 / 配额）在应用的「机器人」页，不在这张原型里 |

| [`owner-workspaces.html`](owner-workspaces.html) | 两种开发逻辑（对话 / 多终端）工作台 | 把「对话开发」和「多终端开发」两种逻辑用同一条外壳强行共用：`TaskPane` 里塞机器人、`TaskChat` 里判四种会话、bot 起的 run 在终端面板里看不到、同一个 bot 三处入口。这一版把 **owner** 做成一等：Bot 工作台（会话为主）/ 项目工作台（终端为主），run 成为可从会话 / TODO / 终端三处独立进入的面 |

| [`project-home.html`](project-home.html) | 项目主页（项目 → 需求，master-detail） | 项目页是卡片墙、需求页是独立外壳，两边靠「页头一个按钮 + 需求页一个项目下拉」连着，在需求页换项目还会把全局当前项目一起换掉。这一版把需求收成**项目主面的一个 tab**：左栏是唯一的项目列表，主面 = 页头一行 + 概览条 + Tabs（需求 / 概览）；运行 / 场景 / 文件是空间与工具，只留一行出口，不占 tab |
| [`pptx.html`](pptx.html) | 演示文稿（pptx 插件视图） | 插件只有 CLI / 命令面板入口，没有界面：参数没处填、大纲确认不可达、页级并发和门禁看不见。这一版把「新建 → 大纲 → 生成 → 结果」收进一个主面（不跳页），左栏生成记录（选中不重排）、右栏本次设置 / 报告 / 门禁 / 产物；并发用每页一张 16:9 卡画出来，失败页就地重试，不重跑整份 |
| [`deckcraft-workbench.html`](deckcraft-workbench.html) | 工作台 · 插件面板（DeckCraft） | 插件只能整页打开，Chat 与工具不同屏；没有元素上下文、安装 / 权限 / 崩溃态。这一版把插件面板 / 整页放进工作台：任务 │ Chat │ 面板同屏，DeckCraft / Excalidraw / Jupyter 多 tab，选中元素进 Chat，面板可装 / 可关 / 可崩，Chat 按插件跑 MCP 改稿 |
| [`entry-points.html`](entry-points.html) | 入口总表（23 张卡，14 个能造出任务的入口） | 上一版把「表 / 时序 / 界面」横向拆成三章，读一个入口要来回跑三次。现在**一个入口一张卡**：卡里就是「条件 / 结果 / 代码 + 时序图 + 界面示意图」，按「这句话从哪儿来」分 8 组 |


### 演示文稿（`pptx.html`）

只回答一件事：**从一句主题到一份原生 `.pptx`，界面上要经过哪几步、每一步看得见什么。**

```
rail 56 │ 左 232 生成记录 │ 主面：新建 / 大纲 / 页级并发 / 结果（同一个面板换内容） │ 右 264 本次设置 · 报告 · 门禁 · 产物
```

- **一个主面，不跳页**：新建、大纲确认、生成进度、结果都在同一块面板里换内容；每个状态只有一个 primary，并且都留在主面（新建 / 确认并生成 / 打开），页头的新建只是普通按钮，不弹窗、不 wizard。
- **参数行内填**：素材（主题 / Markdown / 链接）、页数、模式（精细 / 极速）、配色都在表单里；模式决定「先看大纲」还是「跳过大纲直接并发」。
- **大纲就地可改**：每行 = 页码 + 版式 chip + 标题输入；行尾 chevron 展开要点 / 演讲者备注，拖动手柄排序，`XIcon` 删页、`加一页`。
- **并发看得见**：每页一张 16:9 缩略卡，状态是 排队 / 生成 SVG / 翻译 / 完成 / 失败，卡脚写引擎、单页耗时、门禁角标；顶部一行是「已完成 / 总页 · 并发 · 用时」+ 进度条。
- **失败页可单救**：精细模式的门禁 error 只把该页标失败（结果页写出失败页 ID），页内「重试」或页头「重试失败页」；极速模式同一问题降级成 warning，不阻断交付 —— 这是两种模式唯一可见的差别。
- **结果只有一份**：`deck.pptx` 是唯一交付物（打开 / 在 Finder 显示）；报告、`outline.json`、`slides/*.svg` 是附件，收进 `⋯` 与右栏「产物」。
- **数字不进 chrome**：页数 / 耗时 / 对象数只在结果条、报告 tile、列表行尾出现；tab / 标题不挂计数。

**可点交互**

- 左栏换记录（顺序固定，选中不重排）；`新建` 回行内表单；页头 `ChevronLeftIcon` 回插件市场
- 素材建议 chip → 生成大纲（模拟 700ms）→ 改标题 / 展开改要点与备注 / 拖动排序 / 删页 / 加页 → 确认并生成
- 生成过程（模拟并发 5；第 9 页在精细模式必然失败）→ 取消 → 继续生成；失败页重试 / 全部重试
- 点页卡 → 右栏换「单页」；点门禁条目 → 定位到该页；`返回本次` 回报告
- 结果条：打开 / 在 Finder 显示 / `⋯`（报告 / 大纲 / SVG 快照）；`◐` 切亮暗
- 定格：`?theme=light|dark`、`?state=empty|compose|outline|running|done|failed`、`?run=1|2|3|4`、`?mode=quick|precise`、`?deck=paper|graphite|clay|ink`、`?model=off`

**与实现的关系**：尚未落地。落地时按原型补三处——`PluginMarket.tsx` 的 `VIEW_TARGETS` 注册一个 `pptx` 页面组件、`App.tsx` 的 `View` 加一项、`package.json` 的 `extraResources` 带上 `plugins/pptx`。
插件侧还要补一个**继续生成**（resume）：当前 `pptx.cancel` 只 abort、会丢掉已渲染页；原型按「保留已完成页 → 继续跑剩余页 → 结束才装包 / 落盘」画，需要把 `rendered` 与 `phase = canceled` 一起保留，再补一个 `pptx.resume`（或允许 canceled 状态下 `pptx.retryPage` 逐页续跑）。
另有一处实现冲突要在做界面前修：插件的**精细模式**门禁会把设计器自己的装饰出血算成 `GEOMETRY_BOUNDS` error，导致模板兜底页也被阻断（`--mode precise --engine template` 实测「所有页面都失败了」）。原型按「装饰出血只记 warning、真 error 才把该页标失败」画。

### 工作台插件面板（`deckcraft-workbench.html`）

只回答一件事：**插件可以装，但界面要放在工作台里：任务栏 │ Chat │ DeckCraft 面板。**

```
rail 56 │ 任务 / 项目 320 │ Chat 400 │ splitter │ DeckCraft 面板（插件）
```

- **插件是面板，不是整页**：面板一行 chrome（插件 tab + 页码 + 保存 + `⋯`），没有第二排 ribbon；关掉面板，工作台回到原来的单面布局。
- **多插件 tab**：DeckCraft / Excalidraw 是 panel，Jupyter 是 page（整页工具；原型里缩在右栏预览，并标注 `page`）；点 tab 切换，film / 页码等只属于 deck，选区按插件重置。
- **Chat 不动**：仍是我们自己的 `TaskChat`；插件只通过 RPC 送 `ui.context.set`，不拥有 Chat。
- **选中元素**：DeckCraft 点标题/指标卡 → chip `元素 · DeckCraft · 第 4 页 · 标题`；Excalidraw 点图形 → `元素 · Excalidraw · 画布 · 矩形 1`；Jupyter 点 cell → `元素 · Jupyter · Cell 2 · Code`。
- **Chat 改稿**：按当前 tab 换工具：`deck.*` / `canvas.*` / `notebook.*`；预览即时更新；真实实现见 [`ARCH-plugin-panels`](../arch/ARCH-plugin-panels.md)。
- **安装 / 权限 / 签名**：rail「插件」或任务栏底部「插件市场」→ 安装面板：来源 URL、11.9MB、四条权限（fs:project / ui:panel / ui:context / deck:engine）、SHA256 + 签名说明；装完直接出现在右侧。
- **崩溃隔离**：面板崩了只显示「重载面板 / 查看日志」，Chat 和任务不动。
- **中文**：这里是我们自己的 SVG 预览 + 无头引擎，不嵌 DeckCraft 的 ribbon；DeckCraft Web UI 没有 CJK 字体，中文会是方框。

**可点交互**

- 点标题 / 指标卡 / 图形 / cell → 选中 + 进 Context；`XIcon` 移除上下文；切 tab / 翻页 / `Esc` 清选中
- 发送：无选中时只 inspect；选中标题时改标题并保存；选中指标时只回“要改什么”
- 翻页 / 缩略图 / 左右方向键（仅 DeckCraft）；`⌘S` 保存；`⌘↵` 发送
- `⋯`：在 DeckCraft 中编辑（原生）/ 重载面板 / 面板权限 / 卸载插件
- 拖 Chat 与面板之间的分缝（320–560）；收起任务栏；亮暗
- 安装：`从插件市场安装` → 进度 / 校验 → 面板出现；已安装再看市场是「打开面板 / 卸载」
- 定格：`?theme=light|dark`、`?state=panel|empty|install|crash`、`?plugin=deck|excalidraw|jupyter`、`?deck=paper|ink`、`?page=4&select=title|card-2`、`?fold=task`

**与实现的关系**：尚未落地。插件面板、`workbench.page`、下载安装、通用 `PluginElementContext`、App 托管 DeckCraft 引擎的完整方案见 [`ARCH-plugin-panels.md`](../arch/ARCH-plugin-panels.md)；这里验证「任务 │ Chat │ 面板/整页」的布局、多 tab、选中链路和安装/崩溃态。

### 项目主页（`project-home.html`）

只回答一件事：**项目页和需求页该不该是同一页。**

```
rail 56 │ 左栏 232（唯一的项目列表） │ 主面：页头一行 · 概览条 · Tabs（需求 / 概览）
```

- **页头一行**：项目名 22/600 + `@别名` + 状态 + 分支 + 接手 bot + 路径；右侧只有一个 primary（＋新建需求）和 `⋯`（在 Finder / 执行配置 / 改状态 / 移除）。计数不进页头。
- **概览条**：`任务 · 未完成 · 需求 · 未覆盖`，`0` 不渲染。
- **五个页面级 tab**（不新增 rail 项）：`需求`（树 320 + 详情）/ `看板`（按状态分列，可筛实现者与缺口）/
  `计划`（14 天甘特：按根需求分组、今天基准线、未排期清单）/ `事项`（**台账表格**：遗留事项 / 任务 / 问题 三类记录，一行一条，按更新时间倒序；
  列 = 编号 / 类型 / 标题 / 状态 / 关联需求 / 负责人 / 优先级 / 记录数 / 更新；点行**原地展开**正文、
  处理记录时间线与「记一笔」，动作：标已解决 / 关闭 / 指派 / 转任务）/ `汇总`（**项目汇总**：一句话进展 → 目标 → 里程碑**时间轴**（横向 4 节点，完成实心 / 进行中高亮 / 未开始空心）→ 进展**表格**（编号 / 工作项 / 类型 / 状态 / 负责人 / 说明 / 更新）→ 问题与求助**表格**（编号 / 问题 / 影响 / 需要你）；一列窄版式 ≤760；导出走「导出周报」一个入口：XLSX / Outlook 邮件（.eml）/ Markdown，三档模板见下）。
  看板与计划标注为 **M2 / M3 静态帧**（拖拽、日期编辑、依赖未实现）。
  「事项」是**遗留事项 / 任务 / 问题的台账**（不是任务跟踪、也不是 bot 的 items 视图）：一个表格记下来龙去脉，
  状态是 待处理 / 进行中 / 受阻 / 已解决 / 已关闭；每条带「处理记录」（谁在什么时候做了决定），可转成任务或指派出去。
  真正的任务跟踪（run × 状态 × 时长 × 结论）留在详情「任务」段与工作台，不在这里重复。
  **追溯矩阵不占 tab**：它的日常用法（哪些需求没人接 / 缺验收）已在看板「只看缺口」里，剩下的是审计用途，
  降级成 `汇总 → 交付 → 导出矩阵`（CSV / Markdown）。没有需求时需求池整块换成空态，不留两个空面板。
  从 `requirements.html` 吸收进来的部分：四层 RR→IR→SR→US 与三档裁剪（轻量 / 标准 / 完整，在页头 `⋯` 里切）、
  **状态闸门**（RR 需来源 / IR 需范围+范围外 / SR·US 需验收 / 开始实现需派活 / 完成需验收全勾）、
  验收增删与勾选、子需求、横向关联（相关 / 重复 / 冲突）、**派活**（选实现者建 deliver 任务）、
  缺口 chip（缺验收 / 未派活 / 缺下游），以及**排期字段**（交付层 `起点/终点` → 计划 tab 的甘特条）。
- **概览 tab**：三块 —— 工作（最近运行 / 待确认任务）/ 交付（需求覆盖率与断链）/ 关系（接手 bot / 场景 / 分支 / worktree / 路径）。
- **出口一行**：`去终端 · 去场景 · 打开文件树`；运行不是 tab（它是任务的一次实例），场景是满高舞台，文件是要和终端同屏的工具。
- **交互**：点左栏换项目 = 换主面内容 + 换全局当前项目，**但不跳页**；深链 `?project=p1&tab=req&sel=r3`。

定格：`?theme=light|dark`、`?empty=1`（没有项目）、`?noreq=1`（有项目没需求）、
`?tab=pool|board|plan|items|summary`、`?project=p1|p2`、`?sel=<id>`、`?tpl=light|standard|full`。

**已落地**（2026-11-28）：`src/components/ProjectHome.tsx` + `src/styles.css` 的 `.ph-*` 段，接线在 `src/App.tsx` 的
`view === "projects"`；需求池 tab 复用 `Requirements` 的 `embedded` 模式（去掉自己的页头 / 概览 / tabs）。
主进程补了 `projectSetGoal` / `projectMilestones` / `requirementSetPlan` / `requirementDispatch` /
`issueCreate` / `issueUpdate` / `issueNote` 七个动作，库表新增 `project_issues` 与 `projects.goal|milestones`、
`requirements.plan_start|plan_end`、`todos.requirement_id`。
还没做的：看板拖拽 / 计划里直接改日期。

**易用性收口（第二轮）**：
- 创建入口都能用：页头「新建需求」直接在树顶打开创建行（`n` 同效）；事项「新建」是带正文 / 优先级 / 责任人 / 关联需求的表单；
  里程碑名称回车即可加；目标 `Esc` 取消。
- 看板卡片、计划甘特行、汇总里的进展 / 问题行都能点，落到对应的需求（选中并展开祖先）或事项（展开处理记录）。
- 左栏「全部需求」是跨项目矩阵：搜索、层级筛选、只看缺口，可导出 CSV，点一行跳到那个项目并选中；
  `⋯ → 导出需求表（CSV）` 导当前项目。
- 快捷键（只在项目页、不在输入框里）：`1–5` 切 tab，`n` 新建需求，`Esc` 关掉矩阵 / 事项表单 / 目标编辑 / 里程碑输入。
- 反馈：派活、转任务、复制周报、目标保存、里程碑增删都会在右下角说明结果；复制走主进程剪贴板（窗口没焦点也不会失败）。

**第三轮（把三块静态帧做成能用的）**：
- 看板可拖：卡片拖到别的列 = 改需求状态，闸门会拦（先批准 / 先派活 / 验收勾完），拒绝原因原样提示，状态不动。
- 计划可改期：点甘特条或未排期行的「排期」，行内填起止日期直接保存（不再绕去需求详情）。
- 需求详情新增「任务」段：派活之后在这里看到任务号 / 状态 / 谁在做，点一行跳到工作台。
- 汇总：里程碑逾期标红并写「已逾期」，一句话进展同步改成逾期的说法；只画最近 6 个时注明「复制周报里带全」。
- 汇总改成自己滚（页头与 tab 固定），翻到问题与求助时还知道自己在哪个项目。
- 事项有筛选时给「清空筛选」；派活菜单在没有实现者时说清「去人物里加一个 / 给项目配 bot」。

**第四轮（看板加列表视图）**：
- 交付层现在两种看法：`看板`（按状态分列、拖动改状态）和 `列表`（一行一条，先看在动的：实现中 / 待验收 → 已批准 → 待评审 → 草稿 → 已完成）。
- 列表把状态做成行内下拉，改状态同样过闸门（拒绝时状态退回、原因弹出）；实现者、验收进度、缺口 chip 都在行里。
- 选择记在 `localStorage.ph.boardView`；两个视图共用同一份筛选（实现者 / 只看缺口）。

**第七轮（汇总每一栏都能编辑）**：
- 一句话进展：默认按需求 / 里程碑算出来，点「编辑」手写覆盖（标注「手写」），可一键「恢复自动」。
- 进展 / 问题与求助：表头「＋ 补一行 / ＋ 补一条」加手写记录（标「手写」，可改可删）；
  自动算出来的行进「编辑」只改说明 / 责任人与「需要你」，**来源行本身不会变成手抄**（说明覆盖存在 `notes` 里，页面上标「改」）。
- 存 `projects.report`（lede / progress / asks / notes），导出的 xlsx / eml / Markdown 用的是**编辑后**的这份数据。

**第六轮（周报要能发出去：模板 + XLSX + Outlook）**：
- 汇总不再只有「复制」：右上角一个 `导出周报`，里面三种出去的方式（导出 Excel / 发 Outlook 邮件 / 复制 Markdown）+ 三档模板。
- 模板：`标准周报`（进展 + 目标 + 里程碑 + 问题）、`精简周报`（只进展 + 问题，适合每天发）、
  `交付验收`（里程碑 + 验收明细 + 问题，适合评审）；选择记在 `localStorage.ph.reportTpl`。
- XLSX（SheetJS）：`概览 / 进展 / 里程碑 / 验收 / 问题与求助` 按模板取舍；空数据也出表头，不是坏文件。
- Outlook：生成 `.eml`（MIME + HTML 表格 + `X-Unsent: 1`），双击即以「未发送」草稿打开；中文主题按 RFC 2047 编码。
- 页面渲染与导出共用同一份数据（payload 由 `SummaryPane` 算），Markdown 也交给主进程生成，渲染层不再维护第二份模板。

**第五轮（汇总页头收干净）**：
- 汇总只留一行页头：`本周 11-23 → 11-29` + 右侧一个「复制周报」。删掉了三处重复——
  「项目汇总 · 周报」这种 kicker（tab 已经写着汇总）、接手 bot 列表（页面页头同一份）、
  以及「看板 / 台账」两个按钮（tab 就在上面一行）；页脚原来的「看事项台账」也删了。
- 「本周」改成真正的周一到周日（原来 `±3 天` 的滚动窗口却写「本周」），生成时间退到 tooltip。

没吸收的部分（有意留白）：需求页原来的**全局助手会话**（小A同学）在真实产品里是 rail 底部的全局助手（`⌘⇧A`），
不属于某个项目的页面，所以只在详情里留一个「问小A同学」入口（原型点它只给 toast）。

- `carrier-3d` 的舞台只读现有 `zone / pose / tone / seat`，不新增场景字段；海面有 shader 近舷泡沫带、水线轮廓与舰岛暖光倒影，另有随行驱逐舰 / 补给舰；甲板外沿是一圈薄 catwalk，不是整块板；不再用 billboard / 平面泡沫或甲板下整块 rim 板；舰体顶/底盖与舰艏外露的 hangar 平面也已去掉，低机位不会再从甲板下露出一块灰色长方体。舰体 / 甲板 / 舰载机材质与纹理在运行时生成。3D 只换渲染层，不换调度。
- 质感来源：PMREM 环境反射（金属 / 玻璃）、假地面反射（镜像屏幕 + LED）、地面拼缝、墙面压条、桌面倒角 / 线槽 / 键盘、显示器内框 / 支架、椅子扶手 / 头枕、安全帽 + 耳麦 + 背包；`carrier-3d` 另有甲板防滑颗粒 / 系留点 / 拦阻索 / EMALS 轨道、舰体钢板缝 / 锈迹 / 水线、舰岛窗灯 / AESA / 舷号 18、舰载机面板线 / 红星 / 挂架 / 折翼。
- 已知取舍：没有 Bloom / AO / SMAA；没有贴图法线 / 粗糙度，全凭环境光 + 材质参数；人和椅子是低模；文字分三层（DOM / CanvasTexture / Sprite）。真正做到「照片级质感」需要贴图 + 后期 + 更高模，是另一档预算。

## 动效工作台的结构

```
上：舞台（办公室，四块常驻房间：经理室 / 工位区 / 茶歇区 / 会议室，加审批台、验收架）
下：时间轴（过去 15 分钟的状态变化：10 次变化 · 7 次走位，可拖动 / 回放）
右：Inspector 抽屉（默认收起，点角色打开）
    状态 → 舞台（触发 / 区域 / 姿态 / 动效）
    最近一次走位（可定位回时间轴）
    关闭动效后（reduced-motion 等价检查，找只靠动效表达的状态）
    动效参数（走位时长 / 姿态幅度 / 打字，全局即时生效）
```

三件事必须能对上：舞台上看到的位置，时间轴上能找到对应的那次状态变化，右侧能读到它的触发条件。

**尺寸与自适应**：舞台是固定的 1340×540 画布（工位 180×216 × 6、房间按像素摆好），
页面用 1440×900 设计稿决定 `zoom`（`--z = min(w/1440, h/900)`，下限 0.5、上限 2.6），
再把画布宽高按「窗口 / `--z`」反算，**铺满整个窗口** —— 窗口比 16:10 更宽时不会在左右留白。
舞台再在自己的格子里等比放大并居中（`--k = min(w/1340, h/540)`）。
用 `zoom` 而不是 `transform: scale()`，文字是重新排版的，4K / 外接屏（devicePixelRatio 2）下不糊；
1280 / 1440 / 1920 / 2200 下房间、工位、时间轴的相对位置都不变，也不会互相压。

左右两列房间共用两条横带：左列**经理室 276×190 / 茶歇区 276×164**，
右列**会议室 276×190 / 验收架 240×164**，中间**工位区 690×382**——会议室和茶歇区差不多大。
门都开在朝走道那面墙；Mission `plan_review` 时北从经理室走到会议室，
标签从「空闲」变「会议中」、投屏点亮，时间轴多一条走位。

**光照（四种时段各一页）**：顶部 tab 多了一个「光照」，一屏并排给出 `清晨 / 白天 / 黄昏 / 夜晚` 四张同一时刻的舞台
（克隆当前状态，只换光照），每张右上角写着对应的 URL（`?light=dawn|day|dusk|night`），点任意一张切回实况并固定该时段；
`?view=lights` 直接打开这一页。舞台默认跟本地时间分 `dawn / day / dusk / night`，挂钟和时间轴上的时间也是真实时间；
黄昏与夜晚点亮吊灯、台灯、落地灯和地面光斑，窗外换成夕阳 / 星空 + 月亮 + 城市亮灯，
夜晚把舞台内的表面整体压暗（只改舞台，页面保持亮色）。工具栏「光照」可强制定格，
`?clock=21:30` 固定挂钟、`?light=night` 强制时段，方便截图。

「不是所有状态变化都该走位」是核心判据：失败 / 重试 / 计划批注停在原地，只有真的换了区域才走位；
时间轴上「原地」和「走位」分开标，右侧的 a11y 检查专门找「只靠动效才看得懂」的状态。

**动效工作台的可点交互**

- 点角色 / 工位 → 右侧抽屉打开，展开「状态 → 舞台」和最近一次走位（Esc / ✕ / 「详情」收起）
- 拖动时间轴 → 舞台回到那一刻（走位按当前走位时长回放）；点历史记录 → 定位到该次变化
- `▶ 回放` 依次重放 10 次状态变化；`只看走位` 过滤掉原地变化
- 动效三档（克制 / 完整 / 关闭）+ 走位时长 / 姿态幅度 / 打字，改完立刻生效；`还原默认` 复位
- `走位路径` → 画出区域边界和各角色到目标区域的路径；`模拟 reduced-motion` → 等同关动效，看静态是否可读
- 右上 `◐` 切亮暗；带参数截图：`?view=lights`、`?theme=dark`、`?clock=21:30`、`?light=night`、`?t=300`、`?select=lin&detail=1`、`?paths=1`、`?reduced=1`、`?nowalk=1`

## Bot 的结构

机器人有**两个面**，别混在一起：

| 面 | 管什么 | 在哪 |
|---|---|---|
| 配置页 | 名字、头像、职责、能力档位、绑哪个执行体、日程、配额、暂停 / 静音 | 应用 rail 上的「机器人」（和「项目」同一套骨架：概览条 + 卡片 / 列表 + 行内操作） |
| 会话（`bot.html`） | 它说过什么、为什么说、为什么没说 | 配置页「打开会话」进入；不在 rail 上单独占一格 |

`bot.html` 只画会话这一面：

```
左：bot 会话列表（不是统计面板）——人格、模式、配额都挂在 bot 上
中：回合流——主动 / 回你 是气泡；沉默 / 被拦 / 转人工 是细行，且都能展开「为什么说」
右：Inspector——人格卡 / 记忆四层 / 出场规则，切 tab 不换页
下：以 bot 身份说话（被动回复不受配额限制）
```

三个必须能对上的东西：**这句话是谁说的、它当时记得什么、它为什么现在说**。
`为什么说` 展开后固定四行：触发源、注入的记忆（带 L1–L4 标）、过闸结果、成本；
沉默与被拦同样有这四行，只是注入为空、成本写「没调用模型」——**沉默也要可审计**。

> 试过一版 Orca 式的 sidebar split（机器人列表放在工作区左栏、项目上面，两段可折叠 + 可拖分缝，
> 常量 min 88 / 120）。结论是**机器人需要一块自己的配置面**：配额、执行体绑定、日程这些是
> 「设置一次、长期生效」的东西，塞进左栏会和工作区抢高度，也和工作区的心智（任务 / 终端 / 文件）打架。
> 所以现在改成「配置页 + 会话」两分，左栏回到只服务工作区。

**可点交互**

- 点左栏 bot → 中间回合流与右栏人格卡/记忆/策略一起换（配额、口径都按 bot 隔离）
- `为什么说 / 为什么沉默 / 为什么被拦 / 为什么转人工` → 展开审计四行
- `模拟 1 小时 tick` → 按当前 bot 的配额与静音状态追加一条：正常开口 / 被配额拦 / 静音沉默
- `静音 1h` → 顶部出现静音条，再点 `模拟` 只会追加「静音中」的沉默记录
- dispatch 气泡里的 `起任务 / 先别` → 走「一句话确认 → 桌面审批」闭环：点了「起任务」只建 todo（waiting_input），不会自己起 run
- 上 `◐` 切亮暗；`?theme=light|dark`、`?bot=golo|nan|draft` 定格

`bot.html` 目前是设计原型，尚未落地；字段与规则见 [`../arch/ARCH-bot.md`](../arch/ARCH-bot.md)。

## Mission 动线的结构

`mission-route.html` 只回答一件事：**同一条 Mission 穿过任务面板 / 机器人 / 场景时，事实源放在哪。**

三条动线是三个答案，页面上半部是真实的页面（rail + PageHeader + 一个主 surface），
下半部的「原型 · 动线」条才是原型自己的东西（A/B/C、步骤、说明），不混进应用界面：

```
A 一处派单，三处同影   事实源 = 任务      Mission 只写一次库；机器人在工作区左栏（项目上面），用汇报回合里的 todo 指回，场景只画 delegation（推荐）
B 人物卡，先点人再看活 事实源 = 执行体    任务挂在人身上：点工位 / 点人格卡，打开同一张人物卡
C Mission 时间轴为中心 事实源 = Mission    左列计划、右列 delegation；左栏机器人只留一句指路
```

工作区左栏是一个 pane，三段各自可折叠：

```
TODO     范围（当前项目 / 全部项目）· 新建 · 任务分组（执行中 / 排队 / 待验收 …）
机器人   小Z（主管）+ 小A / 小B / 小C（员工，各自一条任务 T-016/17/18）；点员工，中间换成它那条会话
项目     项目列表 + 未完成数（当前项目高亮）
```

代码里的三处割裂（原型的每一屏都对应其中一条）：

- `TaskPane` 直接用 `state.todos`，Mission 子任务按 `parentId` 缩进 → 任务面板能看见

**可点交互**

`entry-points.html` 是入口清单（文档性质，不是改版方案）：

## Owner 工作台的结构

`owner-workspaces.html` 只回答一个问题：**同一套外壳，能不能按 owner 换主面。**

三层（这一版的原型就按这三层摆）：

```
操作面  BOT（角色）              终端（代码）
        会话 · 过程 · 记忆         项目 · 终端 · 任务表
执行面  Todo → Run → Terminal(pty)                  ← 只有一套
能力面  记忆 · 知识 · 人物 · 视觉                    ← 各自一页，也是工作台里的 tab
投影面  场景                                        ← 只画，不调度
```

```
rail：BOT / 终端 │ 场景 │ 记忆 4 · 知识 4 · 人物 2 │ 视觉 │ 说明 · 设置
  ├── BOT（智能机器人）  主面 = 会话
  │     左：BOT 列表 + 它接的活 · 中：会话 · 右：过程 / 记忆 / 知识 / 人物 / 技能 / 日程
  ├── 终端（智能体终端）  主面 = 终端网格
  │     左：项目列表 + Mission 计划卡 + TODO 总览
  │     中：我的终端 + Agent 的终端 + runbar（三面同源）· 右：文件 / Git / 预览 / 知识 / 执行体
  │     底部：派活 dock（Chat 只是一个 pane）
  └── 记忆 / 知识 / 人物 / 视觉    **复用现有页面**，不重画
        记忆 = Memory（层级 / 注入 / 复核 · 预算）
        知识 = 资料（集合 / 检索 · 引用 / 引擎 · 管道）
        人物 = Persona（人物 / 人设卡 + 证据 / 复核 · 置信）
        视觉 = 视觉解析（任务 / 验证台：原图 ↔ 块 / 后端）
```

**两个操作面的名字**：`BOT`（智能机器人）、`终端`（智能体终端）。rail 和页头共用同一个词；
数据层仍是 owner（`bot` / `project`），不造 `mode` 枚举。

**四个能力页复用现有页面**：不做返回、不套「治理台」、不造第二套入口；工作台右栏里的是同一个能力的**摘要**。

四个必须能对上的东西：

1. **两个左栏同构**：owner 列表（可折叠）+ 这个模式下要干的活。换 BOT / 换项目只有一处入口。
2. **run 三面同源**：会话卡片 → 右栏「过程」→ 终端标签；项目里的 runbar 明说「同一份状态」，
   并且能从终端跳回会话卡片。这是原型里唯一被完整做出来的"跨面对象"。
3. **能力看得到，但不长成操作面**：rail 上是四个页面 + 待办徽标；工作台里是右栏 tab + 左栏能力条。
4. **Chat 派活与 Mission**：终端底部 dock（⌘J）就是 Chat，和 BOT 侧同一个 `send()`，但**只做派活**。
   Super Agent 没有自己的面：Mission 是 `todos(kind=mission)`，owner 是项目，主管是 `role=supervisor` 的 BOT。
   **终端需要它的产物，不需要它的发起**：发起只有一个入口（BOT 里对主管说一句），
   批准只在终端左栏计划卡（因为批准前要对着代码看依赖和 worktree）；
   会话里的计划卡只写「待批准 · 去终端批准」，不同步第二份可编辑计划。
5. **记一条是门铃，不是面**：任何面都能按 ⌘⇧N，落点固定是 TODO。
6. **视觉只有两个入口**：rail 的「视觉」页（验证台）与预览的对象旁按钮，同一个解析、同一个结果。

**可点交互**

- rail 切换两个工作台与四个能力页；`?ws=bot|project|memory|knowledge|people|vision`、`?bot=golo|nan|draft`
- BOT 页：点会话里的 run 卡片 / 左栏任务 → 右栏「过程」跟着换（三处同一投影）
- 终端页：runbar 的「会话卡片」→ 回到 BOT 一侧的同一条 run；「固定到我的布局」→ 终端标签栏出现 `r8122`
- 能力页：左列表 / 中主面 / 右复核队列，按钮都是真实位置（点一下给 toast 说明去向）
- `记一条` / ⌘⇧N → 收集箱；`派活` / ⌘J → 底部 dock；右上 `◐` 切亮暗（默认亮色）
- `?run=r8122|r8126`、`?dock=1`、`?pinned=1`、`?notes=1`

`owner-workspaces.html` 是设计原型，尚未落地。它不改数据模型，只改「谁拥有这一页、面怎么分」。

```
作战室

  中间：长桌 6 席 + 值班指挥（lead）

航母 · 电磁弹射（参考福建舰）
  甲板：舰艏 2 条 + 斜角甲板 1 条 EMALS（CAT 1/2/3，并发 worker）· 1 条着舰道 + 3 道拦阻索（串行 review）
```

两个原型都用 `zoom` 整块缩放（不是 `transform: scale`）：1180×560 的设计稿在不同窗口下

深灰甲板、可见的舷侧与舰岛体积、舰艏 2 条 + 斜角甲板 1 条 EMALS、双升降机、三道拦阻索。
航母整块先在本地坐标里画（舰艏朝上、长宽比按 003 收窄），再整体旋转 +28° 形成参考照片的斜视 2.5D；
HUD、角色标签保持水平，不跟着转。海面用深海军蓝，叠细浪 / 涌浪 / 白浪 / 阳光碎光 / 艏浪尾流，并放两艘护航舰只作尺度参照；
甲板有非滑涂料颗粒、湿痕、胎痕、系留点、猫道格栅、安全网、红色水线、舰岛阴影和折叠翼停放机；
舰体有分片接缝、锈迹、水线藻痕，舰岛有 AESA 网格、舷窗暖光、栏杆和救生筏。

两个舞台都只读 `buildOfficeModel` 已经算出来的 `zone / pose / tone / seat`，不新增字段：

- **并发**：舰艏 2 条 + 斜角甲板 1 条弹射位，对应多个 worker 并行；
- **串行**：着舰道同一时刻只允许 1 架（3 道拦阻索），对应 review / approval 必须排队；

- **原语**：Go / NO-GO、弹射能量、甲板风、拦阻索数都只是 prefs + 只读指标，不改调度。
