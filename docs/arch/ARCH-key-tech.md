## 0. 一句话

```text
① 极小资源 · 高精度解析      真技术（长尾 + 难度量）
④ 记忆系统                  语义设计（记什么 / 忘什么）
⑤ 人物画像                  语义设计（推断可信度）
② 多智能体编排与干预         工程（状态可见 + 干预一致性）
③ Wiki 整理                 产品（自动改对的概率低 → 只能建议）
```

**五件事共用一套底座**，所以不要按五条独立系统去设计：

```text
本地零依赖运行时（Electron 45 / Node 24 / node:sqlite；无 Docker / Python / 原生编译）
        │
  ┌─────┴─────┬──────────┬──────────┬──────────┐
 解析         编排         整理         记忆         画像
 ①           ②           ③           ④           ⑤
  └───── 一把 Ark key（chat / VLM / embedding）─────┘
  └──── 一套确认语义（内容审核 / 记忆确认 / 晋升）────┘
  └──── 一条出口（MCP 只读工具，per-run 子进程 + token）
```

判断新技术值不值得引入，看它是否**同时**满足：能装进 Electron、不新增服务进程、失败时能降级而不是整个模块不可用。

### 0.1 怎么判定一件事是不是关键技术

三条同时成立才算：

1. **有自研/不可替代的工程难点**（不是调一个现成模型）；
2. **失败会让产品不可用**（不是体验降一档）；
3. **换掉它要改架构**（不是换个 provider 就行）。

| 能力   | 自研难点       | 失败后果        | 换它要改架构 | 关键技术   |
| ---- | ---------- | ----------- | ------ | ------ |
| ① 解析 | 有          | 材料不可用       | 是      | ✅      |
| ② 编排 | 有          | 多 Agent 变玩具 | 是      | ✅      |
| ③ 整理 | 有（正确性不可验证） | 体验差         | 否      | ✅（产品型） |
| ④ 记忆 | 有（记/忘什么）   | 上下文被污染      | 否      | ✅（语义型） |
| ⑤ 画像 | 有（推断可信度）   | 半可用         | 否      | ✅（语义型） |


### 0.2 五件关键技术，各自怎么应对（一句话版）

| # | 关键技术 | 应对 |
|---|---|---|
| ① | 解析精度 | 能直抽就直抽，抽不出就渲成图让模型读，读不准就**老实标低置信度**。先量基线再补兜底——现在 OCR 兜底还是空的 |
| ② | 编排与干预 | 让 Agent **主动报状态**，不靠人猜屏幕；人在一个队列里看谁卡住、点批准；子任务传产出物，不传上下文 |
| ③ | 整理 | 后台**只提建议**，绝不自动改审过的页面；先做免费秒级的结构整理，模型只润色摘要 |
| ④ | 记忆 | 四层，越往上越小；每次会话只喂目录（≤12k），往上爬必须**人点头**；空闲才整理，且只能建议 |
| ⑤ | 画像 | 所有推断先进「待确认」，你说「记住」才算数；群聊一句话不算亲密；每条都要能翻出原话和日期 |

共同点：**机器只负责「提出来」，人只负责「点头」，中间每一步都留证据。**（具体设计见 §1–§5 与各模块 ARCH）

## ① 极小资源需求下的各类文档高精度解析


|         |                                                                                                                                                                                               |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 目标      | 单二进制桌面环境下，把 PDF / Office / EPUB / 网页 / 扫描件转成「带页号与标题的 markdown」                                                                                                                                |
| 现在的实现   | `electron/knowledge/parse.mjs`（unpdf / mammoth / xlsx / officeparser / epub2）、`pageimage.mjs`（pdfjs-dist + `@napi-rs/canvas`）、`engines/`（simple / builtin / mineru / paddle / custom + 路由与回退） |
| 已实测     | PDF 文本抽取、页图渲染（980×1268 PNG）、xlsx 表格入库可检索、重复导入去重、删除后重导入正常                                                                                                                                      |
| **硬缺口** | **VLM / OCR 兜底是空实现**：`needsVlm()` 有判据但没有任何调用方，扫描件现在出空页；解析质量**没有任何度量**                                                                                                                         |
| 真难点     | 「各类」是无限长尾：双栏、嵌套表、跨页表、公式、手写、页眉页脚。没有单一方法全覆盖                                                                                                                                                     |
| 关键约束    | 分层（本地直抽 → 页图 → VLM） + **每页给置信度**，低置信度要显式标出，不能假装解析成功                                                                                                                                           |
| 判据      | 20 份真实材料：文本覆盖 ≥95%、表格单元格 ≥90%、引用页命中 ≥90%、recall@5 ≥80%                                                                                                                                        |
| 天花板     | 到不了 RAGFlow / PaddleOCR-VL 那档（要服务进程）；「数字原生 95% + 扫描件靠 VLM 80%」可达                                                                                                                              |
| 优先级     | **P0**（唯一真技术风险，且当前零度量）                                                                                                                                                                        |


要做的顺序：度量脚本 → VLM 兜底 → 表格保结构 → 分块不切断表格 → PDF 阅读顺序 → 质量闸门。

## ② 多智能体编排与实时干预


|       |                                                                                                                                                              |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 目标    | Chat 派活 → 多个 Agent 在真实项目/终端执行 → 人在主界面看状态、必要时干预 → 结果可汇总                                                                                                       |
| 现在的实现 | ACP over stdio（`electron/acp.mjs` + 内置 `dsh`）、`node-pty` 终端、Mission/子任务（`mission_plans` / `delegations`）、审批（`ApprovalModal`）、`todo claim/status` 上报、MCP 工具注入 |
| 真难点   | 不是「起多个 Agent」，而是**状态能不能一眼看懂**、**干预后不产生半成品**、并发写同一仓库的回滚                                                                                                       |
| 关键设计  | 子任务靠 `artifacts` 引用传递（不塞 prompt）；审批落库（谁 / 何时 / 哪个入口）；终端**主动上报**，不解析屏幕文本                                                                                      |
| 判据    | 3 个 Agent 并行同一项目：不翻终端就能说出「谁卡住」；中断后仓库能回到一致状态                                                                                                                  |
| 风险    | Agent 不调 `todo/claim` 就退化成人工盯屏 —— **行为风险**，靠 prompt + 强制工具，不是加监控能解决                                                                                          |
| 优先级   | P1（工程复杂度高，但路径清晰）                                                                                                                                             |

## ③ 知识 Wiki 整理能力


|       |                                                                                                                                |
| ----- | ------------------------------------------------------------------------------------------------------------------------------ |
| 目标    | 把资料沉淀成「带引用、可审核、可回滚」的页面，并在后台做去重 / 补引用 / 标过期                                                                                     |
| 现在的实现 | Source → Page → Citation → Review → Revision、`draft/reviewed/stale`、回收站、双链、图谱、`wiki.curate`（确定性、免费秒级；**只直写 draft，reviewed 产建议**）、`suggestions` 建议队列 + 逐行 diff 审核门、`wikiCurateLLM`（只改摘要/要点） |
| 真难点   | **整理的「正确性」无法自动验证**。合并两页、补引用、标过期，做错比不做更糟                                                                                        |
| 关键设计  | 后台只产**建议**，不直接改 `reviewed`；每条建议带 evidence + `baseHash`；**提议即产物**（批准 = 字节拷贝，不重调模型）；页面已改过 → `needs_rebase` 不自动合并；拒绝也留痕、同类 30 天不重复打扰 |
| 判据    | reviewed 页面从不被静默改写（`wiki:curate:selftest` 断言 = 0）；source 变更后引用页自动 `stale`；建议采纳率 / `needs_rebase` 占比                                         |
| 天花板   | 自动「写出人能用的页面」很难；「结构整理免费 + 模型只润色摘要」是稳的那一档                                                                                        |
| 优先级   | P2（产品问题，先保证不添乱）                                                                                                                |

## ④ 记忆系统能力


|       |                                                                                                                  |
| ----- | ---------------------------------------------------------------------------------------------------------------- |
| 目标    | 做过的事分层沉淀，下次会话注入「对的东西」，顶层永远保持小                                                                                    |
| 现在的实现 | 四层（结论 / 项目 / 事实 / 原始）+ 未验证 note + Dream 建议队列 + 注入预算（≤12k）+ 回查（`memory_search`，MCP 内）+ `memory().inject()` 单一注入来源 |
| 真难点   | **什么该记、什么该忘**。参照 Anthropic 的对照：413 个文件只拿 1 个徽章，9 个文件拿 4 个 —— 记得越多越差                                              |
| 关键设计  | 越高层越小；L1 不可写（Dream 的 ground truth）；晋升必须可追溯且人工接受；Dream 可关、有预算                                                     |
| 判据    | 开 / 关 Dream 的返工次数对比；L4 注入条目被实际引用的比例                                                                              |
| 头号风险  | 自动晋升污染**每一次**会话 —— 因此晋升只能产建议，且要能回到上一个 `memory_version`                                                           |
| 优先级   | P1（已可用，差 LLM Dreaming 的校正/晋升）                                                                                    |

## ⑤ 人物画像构建能力


|       |                                                                                                                    |
| ----- | ------------------------------------------------------------------------------------------------------------------ |
| 目标    | 从聊天记录与资料里构建本人 / 他人 / 关系，带时间、带来源、可确认、可撤回                                                                            |
| 现在的实现 | 四格式导入（Telegram / 飞书 / 微信 txt / CSV，`persona/chat-import.mjs`）、规则抽取、三层画像、双时态 + `asOf` 回看、群聊降权（关系强度 0.3）、候选确认队列、敏感标记 |
| 真难点   | **推断的可信度**。规则抽取宁可漏也不乱猜；模型会编，所以一切推断必须先 `pending`                                                                    |
| 关键设计  | 没有来源不能确认；群聊 ≠ 亲密；`valid_to` 由确认驱动（两个方向都要处理）；矛盾只在「同时有效」时成立                                                          |
| 判据    | 确认队列的误报率；`asOf` 回看与当时对话是否一致                                                                                        |
| 天花板   | 规则覆盖「明确自述」；隐含偏好只能靠模型，而模型必然有幻觉 —— 这是**产品问题**（确认成本 vs 画像价值），不是算法问题                                                   |
| 优先级   | P1（§1 五条 US 已通，剩调优）                                                                                                |

## 6. 难度与风险排序

```text
真技术风险     ① 解析（长尾 + 零度量 + OCR 空实现）
语义设计风险   ④ 记忆（记什么/忘什么） ≈ ⑤ 画像（推断可信度）
工程风险       ② 编排（状态可见 + 干预一致）
产品风险       ③ 整理（自动改对概率低 → 只做建议）
```

不要平均分配精力：**① 是唯一会「做了但看起来不像做了」的模块**（因为看不到精度数字），其余四件的效果用户能直接感知。

## 7. 落地顺序

| 顺序 | 事项 | 工期 | 为什么先做 |
|---|---|---|---|
| 1 | 解析 eval 骨架 + 20 份真实材料标注 | 1 天 | 没有度量，后续「提升」都是猜 |
| 2 | VLM 兜底 + 判据升级（密度 / 图像占比 / 乱码率）+ 按页缓存 | 0.5–1 天 | 页图已能渲，只差接 Ark；扫描件从 0 到可用 |
| 3 | 表格保结构（xlsx / HTML / PDF 聚类） | 0.5 天 | 引用质量的主要来源 |
| 4 | 分块：表格不切断 + heading path 进 chunk | 0.5 天 | 精度一半死在分块 |
| 5 | 3 Agent 并行 + 主界面状态可见性验证 | 0.5 天 | 决定 ② 是能力还是玩具 |
| 6 | PDF 阅读顺序（双栏 / 页眉页脚） | 1 天 | 论文、财报类材料 |
| 7 | 解析质量闸门 + 低置信度标记 | 0.5 天 | 把「静默失败」变成「可见的弱」 |

## 8. 明确不做

| 做法 | 原因 |
|---|---|
| 引入 PaddleOCR / RAGFlow 服务 | 要 Python + 服务进程，与「极小资源」冲突；质量优势只在复杂版式，且 VLM 可覆盖 |
| 让 LLM 整篇重写原文 | 贵，且**不可引用**（无法保证与原文对应） |
| 全量页走 VLM | 每页一次调用；数字原生 PDF 纯属浪费 |
| 追 bbox 级引用定位 | 坐标不稳，页级 + 段级已足够核对（zhulong 接入后可升级为块级） |
| 为记忆 / 画像引入独立向量库 | 个人语料规模下 `node:sqlite` + 暴力 cosine 足够（20k×1024 实测 15ms） |

## 9. 已验证的前提（避免被当成猜测）

| 结论 | 验证方式 |
|---|---|
| `node:sqlite`（Electron 45 / Node 24.22）内置且 **FTS5 可用**、可 `loadExtension` | 运行时 `CREATE VIRTUAL TABLE ... USING fts5` 通过 |
| 中文两字词在 FTS5 默认分词下查不到（`unicode61` / `trigram` 均失效） | 实测查询 `知识库` / `检索` 命中为 0 |
| 暴力 cosine 20k×1024 ≈ 14–18ms/query | 基准脚本跑 5 次取均值 |
| 现有 Ark key 是 **plan 网关** key：`/api/plan/v3` 可用、`/api/v3` 401、rerank 全 404 | 逐个端点实测 |
| `pdfjs-dist + @napi-rs/canvas` 渲染页图稳定；`unpdf.renderPageAsImage` 在 Node 24 抛 transfer 错误 | 两者各跑一次对比 |
| 封面图做 vision embedding 约 1.2 万–2 万 tokens/页（长边 980px） | 实测三档分辨率对比，见 `ARCH-knowledge.md` §7.3.1 |
