# 原始需求 · 按模块

> 状态：原始记录，待逐条确认。只写“想要什么”和少量现状，不展开实现细节。
> User Story 编号：`US-<Module>-<NN>`，例如 `US-ScenePlatform-01`。

## 0. 产品一句话

一个本地优先的控制面，把执行、编排与知识沉淀收进同一套状态，Agent 走向可观察、可审批、可记忆 。

- 多 Agent 工作台：Chat 派活，Agent 在真实项目和终端执行，TODO 看状态，人确认。
- Super Agent：复杂可并行任务才拆主管—子任务，计划先批、结果再汇总。
- 知识：静态资料可查、可引用，只回答“材料里写了什么”；同时沉淀成可审核页面。
- 记忆：四层（transcript / note / 知识 / 注入索引）+ 一个 Dream 循环，后台校正与晋升，顶层保持小。
- 人像记忆：从聊天记录和资料里构建画像（本人 / 他人 / 关系），用来辅助决策。
- 多智能体终端：在既有终端上补状态与审批，回到主界面。
- 即时通信：手机上也能继续处理，关键动作仍由人决定。

## 0.1 状态与确认（术语）

全文档统一使用下面的词，其它小节不再重复定义。

**任务状态**（唯一枚举）

- 待执行 / 进行中（排队、运行中、等待输入）/ 待确认 / 已完成 / 失败 / 取消

**五种确认**

| 说法 | 用在哪 | 谁做 | 结果 |
|---|---|---|---|
| 任务确认 | 任务跑完 | 人 | 任务进入已完成 |
| 计划审批 | 主管出计划 | 人 | 才允许创建子任务 |
| 内容审核 | 知识页面 draft | 人 | 变为 reviewed |
| 记忆确认 | 画像提案 | 本人 | 写入画像 |
| 远程审批 | 终端或任务的动作 | 人（桌面或即时通信） | 动作继续或拒绝 |

**规则**

- 远程审批只覆盖任务级、动作级；计划审批、内容审核、记忆确认默认在桌面完成。
- 任何确认都要留下「谁、何时、在哪个入口」的记录。

## 1. 人像记忆

> 目标：从导入的聊天记录、知识库资料和日常对话中，构建本人、他人和社会关系的画像，用来辅助决策。

### US-Persona-01 从历史资料构建画像

**作为** 有大量聊天记录和资料的用户  
**我希望** 导入聊天记录、笔记和知识库资料，从中抽取关于我、我身边的人、以及我们关系的信息  
**以便** 不用手工整理，也能积累出一份可用的画像

**验收**

- 支持导入微信、飞书、Telegram 等导出的聊天记录，以及笔记和文档
- 能选用知识库中已入库的资料作为抽取来源
- 能从聊天中区分说话人：本人、对话对方、群成员
- 批量导入可中断、可增量；重复导入不产生重复内容
- 每条内容都有来源，能回到原文位置
- 来源不可靠或过旧的内容降权并标记
- 导入结果先进入待确认，不直接生效

**当前**

- 未实现。现有 LLM Wiki 只做“资料 → 页面”，不处理“人”。

**待确认**

- 首批导入哪些来源？是否允许整段聊天记录入库？
- 群聊记录要不要整体排除？

### US-Persona-02 画像分三层：本人 / 他人 / 关系

**作为** 需要长期了解身边人的用户  
**我希望** 画像能分别记录我、我身边的人、以及我们之间的关系  
**以便** 做决定时能看清人的因素，而不是只有我自己的偏好

**验收**

- 本人：身份、偏好、价值观、硬约束、目标、当前处境
- 他人：角色、与本人的关系、沟通偏好、重要日期、关键事件、当前状态
- 关系：类型（家人 / 同事 / 雇佣 / 合作 / 朋友）、强度、方向（谁影响谁、谁依赖谁）
- 同一人的多个称呼、账号、群昵称能合并，合并结果可人工修正
- 群聊互动与一对一分开展示，不把群里的单次互动当成亲密关系

**当前**

- 未实现。

**待确认**

- 他人画像的默认可见范围是什么？
- 合并冲突（同名、同人不同号）由谁裁定？

### US-Persona-03 画像随时间演变

**作为** 想知道“我的想法怎么变成现在这样”的用户  
**我希望** 每条画像内容都带生效和失效时间，并保留演变过程  
**以便** 不把新旧说法混在一起，也能回看当时的情况

**验收**

- 每条事实能说明什么时候开始成立、什么时候不再成立
- 能回答“这个偏好或关系是怎么变过来的”，给出过程而非新旧并列
- 新旧内容明显矛盾时标出来，不静默覆盖
- 能按时间点回看“当时什么是真的”

**当前**

- 未实现。

**待确认**

- 旧内容默认隐藏还是默认显示并划掉？

### US-Persona-04 用画像辅助决策

**作为** 面临真实取舍的用户  
**我希望** 做决定时能同时看到我的约束、相关人的立场、以及过去类似决定的结果  
**以便** 判断有依据，而不是听一段泛泛的建议

**验收**

- 决策时给出：本人约束与偏好、相关人及其立场、过去类似决定和结果
- 能回答“该找谁”“他大概率会怎么反应”“通过谁能接触到某人”“这件事会影响到谁”
- 信息不足时明确标“未知”，不猜、不补全
- 每条结论都能给出来源，让人自己判断可信度

**当前**

- 未实现。

**待确认**

- “类似决定”按什么标准算类似：领域、参与人、金额，还是时间？

### US-Persona-05 确认与隐私边界

**作为** 不希望被 AI 擅自定义、也不希望他人信息外泄的用户  
**我希望** 只有我确认过的内容才算记住，涉及他人的内容有隔离  
**以便** 画像可信、可控、可撤回

**验收**

- 机器推断的内容先进入待确认，只有本人明确说“记住”或审核通过后才生效
- 禁止每轮对话后自动推断写入
- 涉及他人的敏感内容单独标记，默认不对外发送，例如不推到即时通信
- 待确认可逐条确认或拒绝；拒绝也留痕，同类推断不反复打扰
- 没有来源的推断不能提交确认
- 能按人、按时间段、按来源删除

**当前**

- 未实现。

**待确认**

- 拒绝后是否保留“已拒绝”记录供以后参考？敏感级别怎么分几档？

## 2. 知识（资料 + 页面）

> 目标：静态资料可查、可引用，只回答“材料里写了什么”；整理过的页面能沉淀、能被引用、能被追溯。
> **资料侧与页面侧是同一条需求的两种对象，不是两个需求**：资料只读，页面可写可审核。原 §13「LLM Wiki / Notes」是实现路线，已并入本节；实现见 [`ARCH-knowledge.md`](ARCH-knowledge.md)，§13 保留为入口。
> US 编号保持原样，便于与旧版本对照：`US-Knowledge-*` 是资料侧，`US-LLMWiki-*` 是页面侧。

### US-Knowledge-01 资料可查、可引用

**作为** 有大量资料的用户  
**我希望** 资料进来后能检索，答案带出处  
**以便** 不用自己翻文件，也能核实它说得对不对

**验收**

- 资料能导入、能列出、能删除；覆盖本地文件、网页、PDF / Office / EPUB、扫描件
- 检索结果带出处，能回到原文位置（文件 + 页 / 段）
- 中文可检索：两字词也能命中，不是纯子串匹配
- 只回答“材料里写了什么”，不回答“这个人怎么想”
- 与人像记忆互不写入
- 资料本身只读，问答不改原文
- 删除资料时，已引用它的页面要标为过期
- 可以在界面里浏览，但检索不依赖界面

**当前**

- 本机 Markdown 与网页已覆盖导入、引用、审核；PDF / Office / 扫描件与中文检索未实现。

**待确认**

- 是否需要接入内置 Wiki 之外的资料源（飞书 / Notion / GitLab 等）？
- 多个资料源的重复内容怎么去重？

### US-Knowledge-02 一条查询覆盖资料与页面

**作为** 既存资料又写页面的用户  
**我希望** 一次提问就同时命中我存的资料和我写过的页面  
**以便** 不用先判断该搜哪一边

**验收**

- 一次查询同时返回资料片段与页面，结果标明来源类型
- 答案的引用只能来自候选集；资料引用可跳到页 / 段，页面引用可跳到该页
- 无依据时明确说“材料里没有”，不拼接无关片段
- 两类对象用同一套引用解析，不出现两种写法

### US-LLMWiki-01 沉淀可审核知识

**作为** 需要长期积累项目知识的用户  
**我希望** 把资料整理成带引用、可审核、可维护的 Wiki 页面  
**以便** Agent 能检索，人又能控制最终内容

**验收**

- Source → Page → Citation → Review → Revision
- Agent 只能写 draft；reviewed 页面不能静默覆盖
- 支持本地 Markdown 目录导入 / 编辑 / 写回
- 支持 Memory 索引、搜索、图谱、Review 队列
- 通过 MCP 工具让 Agent 检索和写 draft

**当前**

- 已实现 Notes 插件、Source/Page/Citation/Review/Revision、Memory、Dream、图谱、CodeMirror 编辑器、MCP 工具。
- 支持本地 Markdown 目录导入、页面编辑、审核。

**待确认**

- 是否需要更深的 LLM 维护（自动合并、过期检测）？ - 需要

### US-LLMWiki-02 写作不丢内容（P0）

**作为** 每天在 Wiki 里记东西的用户  
**我希望** 正文自动保存、删错能找回  
**以便** 不用惦记 ⌘S，也不怕误删  

**验收**

- 停笔约 1s 自动保存；标签页显示未保存点，保存失败有明确提示且不丢编辑内容
- 页面 / 资料 / 本地文件删除进回收站（默认保留 30 天），可还原到原位置
- 删除动作可撤销（⌘Z 或「撤销」提示条），不会静默消失

**当前**

- 只有 `⌘S` 保存、无自动保存；删除为二次确认后立即生效，无回收站。

### US-LLMWiki-03 记东西零摩擦（P0）

**作为** 随手记录的用户  
**我希望** 一个快捷键就能开写，随手打标签  
**以便** 想法不丢在脑子里  

**验收**

- 全局热键唤起快捕窗口（不切主窗口、不打断当前任务），剪贴板 / 当前选中文本可预填
- `#标签` 补全有真实候选（当前传的是空数组）；标签可点击筛出全部页面
- 有收藏 / 置顶 / 最近打开列表，新建页面后自动进入可编辑态
- 侧栏与插件统一叫法（现为「笔记」/「Wiki」两套词），跟本条一起改

### US-LLMWiki-04 找得到（P0）

**作为** 笔记变多的用户  
**我希望** 中文也能搜到，并直接跳到命中处  
**以便** 3 秒内定位一句话  

**验收**

- 中文按字切分、支持模糊匹配与标题加权（现为纯 `indexOf` 子串）
- 结果高亮命中，点击后滚动并定位到该段
- 可按状态 / 时间 / 来源类型筛选；有搜索历史
- 资料与页面在同一个搜索入口，结果标明类型

### US-LLMWiki-05 双链走完最后一步（P1）

**作为** 靠双链组织知识的人  
**我希望** 链接能悬停预览、缺失的能一键创建、反链能看到上下文  
**以便** 链接是导航而不是装饰  

**验收**

- 预览内 `[[页面]]` hover 出摘要浮层
- 不存在的页面显示为可点击创建（红链），创建后回填标题与出处
- 反链面板显示来源句摘录；另有 unlinked mentions 列表
- 图谱节点可点开对应页面，支持按类型（页面 / 资料 / 本地文件）过滤

### US-LLMWiki-06 问我的知识（P0，差异化主线）

**作为** 积累了大量页面和资料的用户  
**我希望** 直接提问并拿到带引用的答案  
**以便** 不用翻十几页找结论  

**验收**

- 回答每段带出处（`[[页面]]` 或 `[doc:… · p12]`），可点击跳转；无依据时明确说「材料里没有」而不是编造
- 只基于本地检索结果回答；发给模型的只有命中的片段，不上传整库
- 答案可一键存为 draft 页面，走原有 Source → Page → Review 流程
- 现有 `wiki.generate` / `wiki.curate` 是模板拼装，本条才引入模型生成

### US-LLMWiki-07 搬得进、带得走、扛得住（P1）

**作为** 已有笔记存量的人  
**我希望** 整库迁移与导出都是一次操作，规模上去也不卡  
**以便** 不被锁定，也不用重建知识库  

**验收**

- 本地目录可整批导入（去掉当前 30 个上限），失败单个不阻塞
- 导出为 Markdown 目录或单页 PDF
- 1000 页面规模下列表与搜索响应 &lt;200ms；数据量增长不依赖单文件全量读入

**当前**

- 已实现索引与分片：列表 / 搜索只读索引，单页不加载全库，导出仍可还原。
- 1000 页面规模下，列表与搜索保持可用。

**未列入**

- 多端同步 / 共享 / 评论 / 权限：与「本地优先 + 单人」定位冲突，需先定产品方向再谈。

### 边界：两种对象，两套写权限

| | 资料（source / document） | 页面（page） |
|---|---|---|
| 谁写 | 只读导入 | 人写 / 模型写 draft |
| 状态机 | `queued → parsing → ready → failed / stale` | `draft → reviewed → stale` |
| Agent 权限 | 不能写 | 只能写 draft |
| 变更来源 | 源文件 hash 变化 | 人编辑 / 审核 |
| 删除语义 | 删除 → 引用页标 stale | 进回收站 30 天 |

**两者共用**同一套解析、索引、检索入口、引用解析与过期传播；**只有写入侧按上表分开**。

**都不与人像记忆互写**（见第 1 节）。

## 3. 记忆（四层 + Dream）

> 目标：把“做过的事”分层沉淀下来，让 Agent 下一次会话能看到对的东西；**顶层永远保持小**。
> 框架来自 Anthropic《The components of agent memory》：四层记忆 + 一个 Dream 循环。叙事版见 [`ARTICLE-zhihu-llm-wiki.md`](ARTICLE-zhihu-llm-wiki.md)，实现规格见 [`ARCH-memory.md`](ARCH-memory.md)。
> 本节只规定“层次与流动”；L3 里的**资料与页面本身**属于第 2 节「知识」，不在这里重复定义。

### 3.0 四层

| 层 | 内容 | 能否审核 |
|---|---|---|
| L1 Transcripts | 会话、run、工具调用与结果、事件 | 不需要——全量、便宜、只用来回查 |
| L2 Memory Notes | Agent 自己的显著观察、未验证的猜测、踩过的坑 | 不需要，但**可错、可过期、可丢弃** |
| L3 知识 | 资料（只读）+ 页面（可审核） | 需要（内容审核） |
| L4 Injected | 每次会话预加载的目录（≤12k 字符） | 高影响，晋升必须可追溯 |

规则：

- **越高层越小**：L4 是目录，不是书；
- 下层可以被上层引用，上层不得复制下层正文；
- 每层都要能回答“这条是从哪来的”。

### US-Memory-01 四层分明，顶层保持小

**作为** 长期使用这个工作台的用户  
**我希望** Agent 每次会话看到的是一个稳定的目录，而不是一大堆原文  
**以便** 上下文不爆、行为不漂移

**验收**

- L4 注入内容有硬上限（≤12k 字符），超了做减法而不是截断
- L4 只放目录、结论与入口，不放正文
- 能查看“这次会话注入了什么”，便于排查 Agent 为什么这么做

**当前**

- 已实现 `wiki.memory`（≤12k）+ 每次 run 自动注入。

### US-Memory-02 回查发生过什么

**作为** 需要弄清“上次到底发生了什么”的用户  
**我希望** Agent 能主动检索历史会话、run 与工具结果  
**以便** 校正记忆时有事实依据，而不是猜

**验收**

- Agent 有只读工具可检索 transcript / run / 事件
- 检索结果带时间、run、来源会话，能定位到原始记录
- 写入路径不收窄：transcript 只能由系统落库，Agent 不能伪造历史

**当前**

- L1 数据完整（`messages` / `runs` / `events` 在 SQLite），但 **Agent 没有检索通道**；这也是 Dream 目前只能检查知识库自身卫生问题的原因。

### US-Memory-03 记下未验证的观察

**作为** 不希望每次都把猜测写成正式页面的用户  
**我希望** Agent 能写轻量的 note：带置信度、带来源、可以过期、可以丢弃  
**以便** 记得住又不污染已审核的知识

**验收**

- note 是独立对象，不进入页面审核流
- 每条 note 有来源引用，没有来源的不能写入
- note 可标记为已验证 / 已过期；过期的不再注入
- 允许 Agent 写错——纠错成本必须低于“写错一个页面”

**当前**

- 未实现。最接近的是 Source 摘要与 draft 摘要，**它们是 L3 的摘要，不是独立的一层**。

### US-Memory-04 后台整理（Dream）

**作为** 白天干活、晚上不想手工整理的用户  
**我希望** 空闲时自动把 L1 的事实整理成 L2 / L3，并把该晋升的推到 L4  
**以便** 记忆越用越准，而不是越用越乱

**验收**

- 五种动作：**校正 / 构建 / 补洞 / 晋升 / 剪枝**
- 只产建议，**不直接改写 `reviewed` 页面**
- 可关闭、有预算上限；只处理有变更的对象，不定时全量扫
- 每个建议附来源（哪条 transcript、哪个页面），可逐条接受或拒绝
- 拒绝过的同类建议不反复打扰

**当前**

- `wiki.dream` 是**确定性**首轮：缺引用 / 超 7 天的 draft / 重复标题 + 重建 Memory，不调用模型。

### US-Memory-05 晋升与剪枝

**作为** 记忆越来越多的用户  
**我希望** 稳定结论能被推上去，冗余内容能被沉下去  
**以便** 顶层不膨胀，检索不退化

**验收**

- 晋升：note → 页面 → L4 目录条目，每步可追溯
- 剪枝：L3 体积超过原始资料时给出减法建议（合并、下沉、留链接）
- 被剪掉的不是删除：留入口与历史，可回滚

**当前**

- 未实现。

### 边界

| 问题 | 谁回答 |
|---|---|
| 做过什么、当时怎么判断的 | 记忆（本节，L1 / L2） |
| 材料里写了什么、我整理过什么结论 | 知识（第 2 节，L3） |
| 这个人随时间什么是真的 | 人像记忆（第 1 节） |

- **人像记忆不在四层里**：它需要生效/失效时间与“本人确认”，硬塞进 L3 会同时破坏时间语义与审核语义；
- 人像记忆与知识**共享 L1**（聊天记录、run、事件），但**不共享 L2–L4**；
- 记忆不写人像，人像不写记忆。

## 21. 工作树（Worktree）

> ORCA 把 worktree 当“工作空间”：有自己的终端、浏览器、Agent 和布局。  
> 本项目目前把 worktree 当“run 隔离目录”。这一节只要求把它变成**可见、可控的运行上下文**，不要求照搬 ORCA 的完整工作树管理。

### US-Worktree-01 看清任务在哪个 worktree 里跑

**作为** 同时跑多个 Agent 的用户  
**我希望** 任务和终端能看到对应的 worktree 分支、路径，并能打开或清理  
**以便** 我知道改动发生在哪个目录，不会把 worktree 和项目原目录搞混

**验收**

- 任务行 / 终端行显示 `worktree: harness/...`
- 能打开 worktree 目录（终端 / Finder）
- 能清理不再需要的 worktree
- 远端 run 明确显示“不建 worktree，使用远端绝对 cwd”
- 没有 worktree 时不伪造

**当前**

- git 项目派活时自动创建 worktree，分支 `harness/<task>-<run>-<stamp>`。
- 终端模式和 ACP 都会使用 worktree。
- 没有 worktree 列表、分支信息展示、清理入口。
- 远端直接用绝对 cwd，不建 worktree。

**待确认**

- 项目页要不要显示 worktree 列表？ - 理论上需要，但是界面要做好设计
- worktree 信息放任务行、终端行，还是单独一块？
- 清理是手动、任务确认后自动，还是保留 N 天？

### US-Worktree-02 按项目 / 场景决定要不要 worktree

**作为** 需要复用 node_modules、dev server、端口的用户  
**我希望** 能按项目或场景选择 worktree 策略  
**以便** 不是所有任务都被强制放到一个空目录里重新装依赖

**验收**

- 支持 `worktree: auto | always | never`
- 场景 / 项目配置能覆盖默认
- 终端模式遵守该策略
- 手工终端接入任务时，能选择「保持当前目录」或「重启到 worktree」
- 修改策略只影响之后的 run，不改变已有 run

**当前**

- 没有开关；git 项目默认总是创建 worktree。
- 非 git 项目原地执行。
- 场景配置尚未落地。

**待确认**

- 默认用 `auto`（git 才建）还是 `always`？
- 关闭 worktree 时，同一项目多个 Agent 如何避免互相覆盖？
- 手工终端接入任务时，默认保持当前目录还是重启到 worktree？
