# 需求 · 项目需求管理（RR / IR / SR / User Story，可裁剪）

**一句话**：在现有「项目」维度上加一个需求台账 —— 层级（RR → IR → SR → US）可以按项目裁剪，每层有明确准入判据，向下能追到任务 / Run / 提交，向上能被 Agent 读到，**不是再造一个 Jira**。

> **当前分支（feat/requirements-us-ir-sr）**：已落 RR → IR → SR → US 的 M0 —— `requirements` 表、创建 / 编辑 / 状态闸门 / 验收 / 持久化，项目页 + 命令面板入口。看板、助手会话是后续阶段；追溯矩阵已落只读版（路径 / 缺口 / 点 chip 回需求池）。

**为什么现在做**：需求现在散在 `docs/product/REQ-*.md`、Chat、Todo 标题和 Wiki 里；Todo 只有一层，回答「谁在什么时候做」，回答不了「为什么做、做完算不算数」。项目（`projects` 表 + `activeProjectId`）已经是天然边界，缺的是边界里的那条链。

## 0. 结论先行

| # | 决策 | 一句话理由 |
|---|---|---|
| D1 | **项目级，不做全局需求库** | 需求的价值在「和这个项目的代码 / 任务 / 运行对上」；跨项目汇总只做只读视图（后置） |
| D2 | **一张 `requirements` 表 + `level` 字段**，不做四张表 | 裁剪只是换 profile 和重挂父节点，不需要迁移表；状态机 / 链接 / 历史四层共用 |
| D3 | **裁剪在项目级，不按单条需求自由跳层** | 同一项目里一半走四层、一半走两层，追溯矩阵就没法读了；关层不删数据 |
| D4 | **轻索引进 State，正文 / 历史 / 矩阵按需读** | 现有 `broadcast()` 发全量快照；需求正文进 State 会让每次任务操作都重发整库 |
| D5 | **需求 ↔ 任务用链接表，不把需求塞进子任务** | 一条 US 可以被多个任务实现，一个任务也可能覆盖多条 US；交付与验收是两种链接 |
| D6 | **正文是 Markdown + 少量硬字段** | 复用现有 Markdown 编辑 / Wiki 样式；可导出成 `specs/` 给 Agent 读，不引入富文本 |
| D7 | **AI 只产出草稿，批准是人** | 可追溯的 AI 才有价值：每条 AI 草稿带 run 链接，不能自动 approve / 改已批准正文 / 关需求 |
| D8 | **不做自定义字段引擎 / JQL / 工作流设计器 / 权限** | 先窄后宽；四类状态 + 每层 5 个字段就够跑完整条链 |

## 1. 术语与层级

| 层 | 名称 | 回答的问题 | 典型来源 | 叶子？ |
|---|---|---|---|---|
| **RR** | 原始需求（Raw Requirement） | 谁在什么场景下、因为什么、要什么 | 客户、销售、内部、数据、缺陷 | 否 |
| **IR** | 初始需求（Initial Requirement） | 产品化之后「做什么、不做什么」，范围与优先级 | 产品从 RR 归纳 | 否（可裁剪） |
| **SR** | 系统需求（System Requirement） | 系统必须表现成什么样，可验证、可分配 | 研发 / 架构从 IR 拆 | 否 |
| **US** | 用户故事（User Story） | 一个可交付切片：角色 + 价值 + 验收场景 | 研发 / 产品从 SR 切 | 是（若启用） |

> RR / IR / SR 三层 + 可裁剪是孤波 OneFlow 的主线口径（按其公开产品资料；具体字段以试用为准）。
> 本仓库 `docs/product/REQ-*.md` 已经在用 `US / IR / SR` 编号，本模块的编号规则刻意和它对得上，方便导入自检。

**层级不变量**

1. 子项只能挂到**当前启用的最近一层**；裁剪掉中间层时，子项直接挂到更上一层（如 RR → US）。
2. 父节点必须是**更上游的层**，不能同层互为父子（US 之间用 `relates`，不用父子表达依赖）。
3. 一条需求只有一个父节点；跨项目的父子关系不允许（M0）。
4. 层级只由 `level` 决定，不靠 key 猜；`level` 一旦有子项或已批准，不允许改。
5. **RR 必须启用，至少保留 2 层**；最低的启用层叫**交付层**（可以是 SR，也可以是 US），任务只挂交付层。

### 1.1 界面上的概念（七组）

| 组 | 概念 | 用户在哪里看到 | 说明 |
|---|---|---|---|
| 作用域 | **项目** | 页头项目选择器 | 需求页永远只显示一个项目；切项目 = 换整棵树 / 整块板 |
| 对象 | **需求** | 树里的行、主面详情 | **只有一个对象**；RR/IR/SR/US 是它的 `level` 属性，不是四个模块 |
| 对象 | **任务 / 运行** | 详情「任务」分节 | 既有 Todo / Run，不复制；任务页有「上游需求」深链回来 |
| 对象 | **全局助手 Bot** | rail「小A同学」、会话头部、详情「助手」 | 唯一的 `bots` 记录（`scope=global`）；管所有需求、教软件用法、指挥执行 Bot，不进入 deliver 任务 |
| 对象 | **执行 Bot** | 详情「实现」、任务区、看板 / 甘特 | 任务上的 `botId`；一个需求可以分给多个执行 Bot |
| 对象 | **基线** | 时间线里的「基线 v1」 | M2：冻结一批已批准需求的快照 |
| 配置 | **裁剪方案** | 页头 `⋯ → 裁剪与字段` | 一个项目一份：模板 + 层开关 + 每层闸门 |
| 配置 | **豁免** | 矩阵里的 `⤳`、详情验收区 | 规则 + 理由 + 谁 + 何时；和「缺口」分开显示 |
| 关系 | **父 / 子** | 树缩进、详情顶部的上游链路 | 唯一父节点；裁剪时直接挂到最近启用层 |
| 关系 | **关联 / 依赖** | 详情「关联」分节；计划视图的箭头 | relates / duplicates / conflicts / **depends_on**（只给甘特用，不替亲子层级） |
| 关系 | **实现 / 验收** | 详情「任务」分节 | deliver（谁做）/ verify（怎么验），两种链接 |
| 派生 | **实现者（执行 Bot）** | 详情元信息行、交付层行尾、看板卡片、甘特左列 | 从 `deliver` 任务的 `todos.botId` 聚合，父级只读汇总；需求上不存实现者字段 |
| 派生 | **派活计划** | 助手会话里的提案卡 | 任务 / 执行 Bot / 工作区 / 是否开跑；人点「批准并派活」才生效 |
| 标识 | **层级** | key 前缀 `CMH-SR-12` | rr / ir / sr / us；决定可用字段与允许的子层 |
| 标识 | **交付层** | 树里最低的一层；任务区的落点 | 最低启用层；SR 或 US |
| 信号 | **状态** | 行首状态点、元信息行 | 四类八态（§3.3），不是对象 |
| 信号 | **缺口 / 待复核** | 行尾小字、矩阵单元格 | 六个可计算信号（§5.2）；`0` 不显示 |
| 视图 | **需求池 / 看板 / 计划 / 追溯矩阵 / 裁剪抽屉 / 需求会话** | Tabs、float 抽屉、右侧会话栏 | 是视图，不是新对象；不增页面 |
| 会话 | **助手会话 / 提案卡** | rail「小A同学」/ `⌘⇧A` / 需求详情「问小A同学」 | 同一个 Bot 的不同 thread；以提案卡回复，应用前不改数据 |

**一句话**：用户在界面上只会看到「一个项目、一棵需求树、一条需求详情、两张视图、一个抽屉、一个助手会话」；四层的差别只体现在**编号前缀、可用字段、允许挂的子层、矩阵列**，而不是四套页面。

## 2. 参照与不照抄

| 参照 | 它的做法 | 抄什么 | 不抄什么 |
|---|---|---|---|
| **Jira** | 可配置 Issue Type 层级（Epic → Story → Task）、链接类型、工作流、版本、保存的过滤器（JQL）、看板与审计历史 | 链接类型的**语义少数派**（relates / duplicates / conflicts）、版本即基线、每条变更留痕、列表过滤 | JQL、自定义字段系统、拖拽工作流设计器、权限方案、工时 / 甘特 |
| **孤波 OneFlow** | RR / IR / SR + User Story、按项目裁剪层级、追溯关系与基线，强调「需求 — 设计 — 测试」贯通 | 四层编号、裁剪模板、追溯矩阵、基线快照、每层准入判据 | 评审会 / 评审流程管理、重型配置后台 |
| **Linear** | 键盘优先、打开即用、极少配置；项目 / 周期 / 单 Inbox | 列表稳定性（点了不重排）、快捷键、默认极简、状态只分四类 | 用 Cycle / 自动 backlog 搬运替人做决定 |
| **Multica**（`third-part/multica @ 58b5c66`） | Issue 直接派给 Agent：认领、汇报、挂阻塞、交回评审；生命周期只有 unstarted / started / done / closed 四类，自定义状态但不做工作流引擎 | 「意图 — 运行 — 决策 — 提交」挂在同一个对象上；四类状态；Agent 是执行者不是审批者 | 自建状态目录的后台、按状态自动触发 Agent 的隐式行为 |
| **GitHub Spec Kit / Kiro / OpenSpec / BMAD** | 规格是仓库里的 Markdown：`spec.md` / `design.md` / `tasks.md`，验收用 EARS / Given-When-Then，Agent 直接消费 | 需求正文可机读、验收判据用固定句式、任务从规格派生、`specs/` 单向导出 | 把唯一事实源只留在 repo 里（人要在界面上管理）；多套 agent 角色剧本 |

**一句话取舍**：**管理面学 Jira / OneFlow，使用手感学 Linear，执行链学 Multica，交付物学 Spec Kit。** 每一样只取一层，不叠加成第四套体系。

## 3. 数据模型

### 3.1 字段（少而硬）

| 字段 | 说明 | 必填层 |
|---|---|---|
| `id` | 内部 id（`r…`） | 全部 |
| `projectId` | 项目；需求页永远单项目 | 全部 |
| `key` | `CMH-RR-12`（项目别名 + 层 + 项目内序号），创建后不改 | 全部 |
| `level` | `rr / ir / sr / us` | 全部 |
| `parentId` | 当前启用层的上一级 | 非根层 |
| `title` | 一行标题（≤200） | 全部 |
| `body` | Markdown 正文（背景 / 场景 / 约束 / 设计意图） | RR、IR |
| `status` | 见 §3.3 | 全部 |
| `priority` | `P0 / P1 / P2 / P3` | 全部 |
| `owner` | 责任人（自由文本，不建账号体系） | SR、US |
| `source` | `customer / internal / data / defect / ai` + 一句来源说明 | RR |
| `acceptance` | 可判定验收（字符串数组，一条一个判据） | SR、US |
| `tags` | 自由标签 | 可选 |
| `meta` | 每层固定扩展：IR 的「范围外」、US 的「估算 / 依赖」、waiver 记录 | 可选 |
| `planStart / planEnd` | 计划起止（epoch ms，可空）；只给看板 / 甘特与「本期」筛选使用 | M3，可选 |
| `aiSource` | 生成它的 run / bot；人写为空 | — |
| `approvedAt / approvedBy` | 批准留痕 | — |

**验收判据的写法**（界面给模板，不强制解析）：

- SR 用 EARS 简化式：`当 <触发>，系统应 <可观察行为>，在 <条件> 下`。
- US 用 Given / When / Then，一条一个场景。
- 判据必须能回答「怎么算没做到」；只写「体验良好」「性能优化」不算。

### 3.2 编号

- 项目前缀取 `projects.alias` 的大写字母数字（无则取项目 id），如 `CMH`。
- `key = <PREFIX>-<LEVEL>-<项目内全局序号>`，序号按项目递增，不按层重置（`CMH-RR-12` 之后是 `CMH-IR-13`）。
- key 创建后不变；跨项目移动（M2 才允许）保留旧 key 并在时间线记一条「原属项目」。

### 3.3 状态：四类，不做工作流引擎

借 Multica 的四类生命周期，固定 8 个状态，不开放自定义：

| 类 | 状态 | 含义 |
|---|---|---|
| **unstarted** | `draft` 草稿 · `reviewing` 待评审 | 还在写 / 等人看 |
| **started** | `approved` 已批准 · `in_progress` 实现中 · `verifying` 待验收 | 算「进行中的活」 |
| **done** | `done` 已完成 | 验收判据全过 |
| **closed** | `rejected` 已拒绝 · `obsolete` 已废弃 | 终态，保留原因与链接，不删 |

**闸门（缺一项就不让推，不是弹 toast，是把缺的字段聚焦出来）**

| 迁移 | 条件 |
|---|---|
| `draft → reviewing` | 标题 + 正文 + 来源；上游已进入 reviewing 或更后 |
| `reviewing → approved` | 该层必填字段齐全（RR 来源 / IR 范围外 / SR·US 验收）；上游 `approved`，或对该条记 waiver |
| `approved → in_progress` | 至少一条 `deliver` 任务链接 |
| `in_progress → verifying` | 所有 `deliver` 任务完成 |
| `verifying → done` | 验收判据全部勾选；RR 额外要求提出人确认（`approvedBy` 不为空） |
| 任意 → `rejected / obsolete` | 必填原因；不删除子项和历史 |
| 任意 → `draft` | 只允许 `approved` 之前；已批准的需求改回草稿等于作废，走 `obsolete` |

**豁免（waiver）**：裁剪、外部依赖、一次性实验都可能让某条规则不适用。waiver 要写 `rule + reason + 谁 + 何时`，在矩阵和缺口里显示「已豁免」，不显示成缺口。**没有 waiver 的缺口不允许被静默忽略。**

**派活是状态推进的唯一快捷方式**：`approved` 的需求成功派出一条 deliver 任务时，自动进 `in_progress`，时间线记一条「派给 小B · 任务 #123」；撤销派活（删任务）回到 `approved`。其余状态一律手动推。

### 3.4 与任务的关系

```
RR ── IR ── SR ── US ──┬── deliver ── Todo ── Run ── 提交 / PR
                        └── verify  ── Todo（验收）
```

- 需求回答 **why / what**，任务回答 **who / when**；两者不做父子替代。
- 一条 US 可以链多个任务；一个任务只能有一个主需求（`deliver` 唯一），但可被多条需求 `verify` 引用。
- 任务完成不自动把需求置 `done`；需求 `done` 必须有验收判据勾选（人确认）。
- 需求页派活复用 `createTodo`：`title` 取 US 标题，`desc` 取 US 正文，`acceptance` 取 Given/When/Then，`projectId` 取需求所属项目。

### 3.5 全局助手：一个 Bot，管所有需求，也告诉你软件怎么用

**整个工作台只有一个全局助手 Bot**（UI 叫「小A同学」），不是每个项目一个，也不是每条需求一个。它是 `bots` 表里的记录（`scope='global'`、`role='supervisor'`），有名字、头像、人格、执行体、预算、回合审计。

**它做三类事**

| 能力 | 具体动作 | 人怎么把关 |
|---|---|---|
| **管需求** | 跨项目读所有需求；补验收 / 改草稿 / 拆下游 | 提案卡，勾选后应用，只写 draft |
| **指挥 Bot** | 派活、改派、停 run、查进度、催办；可跨项目 | 派活 / 停 run 用提案卡；人批准或人授权 |
| **教用法** | 回答「设置在哪」「怎么建需求 / 派活 / 看进度」；给步骤 + 「带我去」 | 只读导航；引用 Guide / docs / UI map，不知道就说不知道 |

**它是全局的**：所有项目、所有需求共用同一个助手；需求会话只是它的一个 thread，不是另一个 Bot。项目里只有执行 Bot，没有自己的主管。

**授权由人给，不是默认能力**：默认每一步都问。人可以给助手三种授权：

| 授权 | 范围 | 约束 | 撤销 |
|---|---|---|---|
| 单次 | 这一次派活 / 开跑 | 只对当前计划 | 用完即失效 |
| 本会话 | 当前需求 thread 的同类操作不再逐次问 | 只限派活 / 开跑 / 改派 / 停 run | 会话头「撤销」 |
| 本项目 | 本项目所有已批准需求 | Bot 白名单、每日任务上限、并发上限、工作区、工作时间 | 设置里撤销，写审计 |

授权只开放「派活 / 开跑 / 改派 / 停 run」；**批准需求、关需求永远不授权**。每次授权 / 撤销 / 按授权自动执行都写审计。

**停 run / 关需求先看任务状态**：

- **停 run**：只有当 run 处于 `running / waiting_input` 才出现提案；卡里带任务、Bot、已运行时长、最近事件、原因。人批准后停；授权也只对匹配的 run 生效。
- **关需求**：先检查 `deliver` 是否全部完成、验收是否全勾、`verify` 是否完成或豁免；缺什么就列什么，缺一条都不能关。**即使有授权，关需求也永远要人确认。**

**它不能做什么**：不能 `approve` 需求，不能改已批准正文，不能在无授权时自动派活 / 开跑 / 停 run，不能自动关需求，不能跳过 waiver 规则。预算与 turn 上限沿用 Bot 档案（`bots.budget` / `policy`），每一轮都有审计。

**和实现者的边界**：助手是「指挥」，实现者是「执行」。助手本身不挂 `deliver` 任务，不计入实现者聚合；换助手（全局只有一次）不会自动改已派出的任务。

**数据**：`settings.assistantBotId` 指向唯一的全局助手；`threads.bot_id` = 它，`threads.project_id / requirement_id` 表示上下文；`requirement_mandates.bot_id` = 它，`project_id` 表示授权范围；派活计划作为 tool result 落库。

### 3.6 实现者：从任务派生，不在需求上存 Bot

**规则**：需求本身**不存** `assignedBotId`。谁在实现由 `deliver` 任务上的 `todos.botId`（派给谁）与 `runs.agentId`（实际执行体）决定；父级需求（RR / IR / SR）的「实现者」是所有后代交付层任务的**只读聚合**。

理由：

1. 一条 SR 下的 US 常常分给不同 bot；在需求上存一个「主责 bot」必然和任务漂移。
2. 「交给 bot」不是归属，是**派活**：没有任务就没有执行单元，也无法验收。
3. 改派只改任务，需求自动跟着变，不需要两处同步。

**派给谁 = 建任务**：

- **交付层派给执行 bot**（SR 或 US，看裁剪）；**父级只能交给助手 Bot 拆解**（建 mission 任务），不能把父级直接派给员工 bot 当交付。
- 派活弹层：选执行 bot / 助手（建 mission 任务）/ 指定执行体（agent）、工作区（项目根 / worktree / bot 已有工作区）、是否立即开跑。
- 写入 `todos.botId` + `requirement_tasks(deliver)`；approved 的需求顺带进 `in_progress`，时间线记「派给 小B · 任务 #123」，可撤销。
- 助手 Bot 拆出的子任务也写回同一条需求（`deliver`）；实现者视图显示「助手 小A同学 → 小B / 小C / 小D」。
- `verify` 任务可以派给另一个 bot（评审者），和实现者**分开显示**，不混进「实现」。

**四种可见状态**：

| 状态 | 判据 | 界面 |
|---|---|---|
| **未派活** | 交付层已批准，没有 deliver 任务 | 「未派活」+ 派活按钮；计入 `unplanned` 缺口 |
| **已派给 Bot** | 有 deliver 任务且 `botId` 非空 | 头像 + 名字 + 任务进度 `1/2` |
| **手动任务** | 有 deliver，但 `botId` 为空 | 「手动任务」+ 执行体 agent |
| **已交付待验收** | deliver 全部完成 | 头像弱化 + 「待验收」；不算 `unplanned` |

**改派 / 停用 / 多人**：改派 = 改任务的 `botId` 并记时间线，不新建重复任务；bot 停用后头像保留并标「已停用」，历史不消失；多 bot 就显示头像叠放 + `N 个 Bot`，点开是任务明细，不硬选一个「主责」。

## 4. 裁剪（tailoring）

### 4.1 三个模板 + 自定义

| 模板 | 层级 | 用在什么项目 |
|---|---|---|
| **轻量**（2 层） | RR → US | 内部工具、小团队、需求与交付一步到位 |
| **标准**（3 层） | RR → SR → US | 大多数研发项目：RR 说为什么，SR 说系统怎么表现，US 说怎么交付 |
| **完整**（4 层） | RR → IR → SR → US | 多角色产品线：IR 承担「做什么 / 不做什么」的范围决策 |
| **自定义** | 任意 ≥2 层，顺序固定 | 明确知道自己不要哪层，并且愿意承担矩阵复杂度 |

- 裁剪是**项目级配置**（`requirement_profiles`），一改影响整个项目；不允许单条需求自己选择跳层。
- 层顺序固定为 RR → IR → SR → US，不能把 US 放到 SR 上面；不做「US 直接挂 RR，同时又有 IR」的混合。
- 至少保留 2 层（只有 RR 就没有交付物，只有 US 就没有来源）。

### 4.2 关层 / 开层的动作（必须显式、可预览、可撤销）

| 动作 | 行为 |
|---|---|
| 关掉某层 | 先算影响：该层有多少条、其中多少已批准、会影响多少子项；抽屉里显示「3 条 IR 的 5 个子需求将上挂到 RR」 |
| 确认关闭 | 子项 `parentId` 改到**最近的启用祖先**；被关层的需求**不删**，标 `hiddenByProfile`，重新开启后恢复原位（用 `meta.detachedFrom` 记住原父） |
| 重新开启 | 恢复原父；若原父已被删 / 已不可见，落到最近启用祖先并在时间线提示 |
| 有未完成迁移 | 迁移失败整批回滚；不允许一半关一半留 |

**不变量**：任何时刻，`parentId` 必须指向「启用的、更上游的」层；否则保存直接失败。这是矩阵和覆盖检查的唯一前提。

### 4.3 每层可调（不做字段引擎）

| 项 | 可选值 | 默认 |
|---|---|---|
| 该层是否启用 | 开 / 关 | 按模板 |
| 是否需要评审 | 是 / 否 | RR、IR 需要；SR、US 不需要 |
| 必填字段 | 从该层固定字段里勾选 | 见 §3.1 |
| 验收判据最少条数 | 0 / 1 / 2 | SR、US 为 1 |

状态机不随裁剪变化（四类八态固定），只跳过被关层的「评审」环节。

## 5. 追溯、覆盖与变更影响

### 5.1 追溯矩阵

- 行 = **一条需求链**（从 RR 到最低启用层的叶子；缺下游的节点单独成行，这样分支缺口不会被兄弟节点盖住）；列 = 启用的层，RR 作为分组表头。
- 单元格 = 该链在该层的那一条需求，四种状态：`✓` 已批准、`○` 进行中、`—` 缺（算缺口）、`⤳` 已豁免。
- 空格 `— ＋` 只在「上一列已有值」时可直接新建；更下游显示 `—`（必须先补上游），避免建出断链。
- 缺口的单元格可点，直接在该格**行内新建**子项（预填父节点与层级），不弹窗、不跳页。
- 顶部筛选：全部 / 只看缺口 / 只看未批准；底部导出 Markdown / CSV（M2）。
- 窄屏：横向滚动限制在主面内部，不撑破页面；分组表头 sticky。

### 5.2 六个可计算信号

| 信号 | 判据 | 显示位置 |
|---|---|---|
| `orphan` | 非叶子层已批准，但没有启用层的子项 | 矩阵空格 / 列表行尾小字 |
| `missing_acceptance` | SR / US 的 `acceptance` 为空 | 详情验收区 + 缺口筛选 |
| `unplanned` | 已批准的最低层需求没有 `deliver` 任务 | 详情「任务」区 + 缺口筛选 |
| `unverified` | `deliver` 任务全部完成，但没有 `verify` 链接 / 验收记录 | 详情 + 项目概览「未验收」 |
| `stale` | 子项批准之后，上游被改过（`parent.updatedAt > child.approvedAt`） | 列表行尾「需复核」chip |
| `broken_link` | 父节点不存在 / 层级不合法 / 指向已关层（自检，正常应为 0） | 设置里的「数据自检」 |

计数只出现在**内容区**（概览条 / 分组行尾 / 缺口筛选结果），不进 tab、标题、图标行；`0` 不渲染。

### 5.3 变更影响

保存已批准需求时：

1. 递归取下游（子需求）、`deliver` 任务、未完成基线快照；
2. 保存前在抽屉里显示「将影响 3 条已批准需求 / 2 个任务」，人确认后才写；
3. 写入后把下游标 `stale`，**不自动降级状态**；
4. 时间线记一条「变更 + 影响范围」，AI 草稿额外带 run 链接。

## 6. AI Agent 怎么接

### 6.1 交互形态：一个全局助手，所有需求和用法都找它

**整个工作台只有一个助手 Bot**，所有项目 / 所有需求共用。每条需求一个**助手 thread**，直接复用现有 Chat 界面：气泡、流式、停止 / 重试、tool 卡、composer、上下文 chip。助手不是只会填表的 AI：它管需求、教软件用法，也能**指挥执行 Bot**（派活、改派、查状态、催办）。

| # | 你问助手 | 它回什么 | 边界 |
|---|---|---|---|
| 用法 | 设置在哪 / 怎么建需求 / 怎么派活 / 这个错误怎么办 | 步骤 + **「带我去」** 按钮（打开页面 / 面板 / 设置） | 只读导航；引用 Guide / docs / UI map；不知道就说不知道 |
| 需求 | 补验收 / 改正文 / 补来源 | 验收 / 正文**提案卡** | 勾选 + 应用才落；一律 `draft`；已批准不可覆盖 |
| 拆解 | 把这条拆成下游 | 下游草稿**提案卡** | 人勾选后应用 |
| **派活** | 拆成任务，小B 实现、小C 验收 | **派活计划卡**：任务 / 执行 Bot / 工作区 / 是否开跑 | 点「批准并派活」才建任务或开跑；**不能自动派** |
| 改派 | 把小B 的任务改给小C | 改派提案卡（任务 + 新 Bot + 原因） | 人批准后改 `todos.botId`，记时间线 |
| 查执行 | 谁在跑、谁卡住、哪个项目没派活 | 任务进度卡：任务 / Bot / 状态 / run 链接 | 只读；可以继续问或发起改派 |
| **停 run** | 小B 卡住了，停掉 | 停 run 提案卡：任务 / Bot / 状态 / 已运行时长 / 原因 | 必须先查任务；人批准；可授权「停 run」 |
| **关需求** | 这条可以关了吗 | 关闭提案 + 还缺什么（任务 / 验收 / verify） | 缺一项都不给关；**关需求永远人确认** |
| 汇总 | 本周哪些没派活、哪些验收没过 | 清单 + 建议 | 只读 |
| 捕获 | 在 Chat 里 @ 需求 / `⌘⇧K` | RR 草稿 | 捕获后仍是 draft |

**因为它是全局的，所以有两个入口层级**：

- **助手主页**（rail「小A同学」或 `⌘⇧A`）：不绑定需求，可以问软件用法、跨项目汇总、让助手找「哪个项目还没派活」；
- **需求 thread**（需求详情「问小A同学」）：绑定当前需求，问补验收 / 派活 / 看进度；顶部带项目 + 需求上下文 chip，避免跨项目串味。

**为什么不做独立的 AI 面板**：模式 / 目标字段 / 提示词那套表单，等于在需求页里重新发明一个更差的 Chat；而且入口只能塞进 `⋯`，越藏越深。会话是用户已经会用的界面，提案卡承担结构化，用法问题用「步骤 + 带我去」卡片承担。

**助手的硬闸门**：

- 可读：所有项目的需求、任务、run、Bot 状态 / 负载、worktree、审批、Guide / docs；
- 可写（必须人点批准，或落在人授予的授权范围内）：需求 draft、子需求、任务、派活 / 改派、停 run；
- 不可：`approve` 需求、改已批准正文、自动关需求、跳过 waiver；
- **跨项目动作必须带项目 / 需求上下文**：助手的上下文 chip 写明「当前项目 / 当前需求」，跨项目操作会在提案卡上再标一次项目，避免在 A 项目里改了 B；
- **授权由人给**：单次 / 本会话 / 本项目，可随时撤销；授权范围只到「派活 / 开跑 / 改派 / 停 run」，到不了「批准 / 关需求」；
- 预算 / 每小时回合 / 静默时段沿用 Bot 档案；每轮带 `bot_turn` 审计，能追到它看过什么、调了什么工具、哪一步是按授权自动执行的。

### 6.2 上下文与交付物

- **注入**：派活 / Mission 时把需求包（RR 摘要 + IR 范围 + SR 规格 + US 验收）拼进现有 context envelope，不新造一套。
- **内置工具 / MCP**（按 `ARCH-agent-bridge` 的窄通道原则，M3）：
  - 读：`requirements_search(query, project)`、`requirements_get(key)`、`requirements_children(key)`、`bots_list(project)`、`tasks_status(requirementKey)`；
  - **用法**：`guide_search(query)` 读 Guide / docs；`ui_map()` 读当前页面 / 可用入口；回答必须给页面路径，不知道就说不知道并打开 Guide；
  - **带我去 / 联动**：tool result 可带 `page` + `action`；动作白名单 `ui_open(view)` / `ui_filter(status|level|query)` / `ui_select(requirementId)` / `ui_focus(section|field)` / `ui_drawer(assign|tailor)`，渲染层执行并高亮，不写数据；
  - 写：`requirements_draft(parentKey, payload)` 只出草稿；派活只出 `requirements_dispatch_plan`，真正的 `requirementDispatch` 由界面在人点「批准并派活」后调用；run 内写操作要审批；
  - 默认只读，助手不能绕过提案卡直接改任务。
- **导出到仓库**（单向，显式动作）：`<project>/specs/requirements/<key>-<slug>.md` + `index.md`；front matter 带 key / level / status / parent / acceptance，正文即 Markdown。仓库里的 spec 是给 Agent 读的快照，**不是第二事实源**；改仓库不回写数据库。

### 6.3 判据

- AI 生成的下游草稿，人采纳率可统计（`aiSource` 不为空且最终 `approved` 的比例），M3 再看，不作为上线门槛。
- 任何 AI 产出的需求都能从 `aiSource` 一键跳到那次 run 的轨迹；跳不过去算缺陷。

## 7. 界面

> 可点的静态原型：[`../prototype/requirements.html`](../prototype/requirements.html)（单文件、双击打开、亮暗可切；看板 / 甘特为 M2/M3 静态帧）。

### 7.1 入口与外壳

- **外壳**：全宽工作台（与知识库 / 记忆 / 人物 / 设置同一套，左栏 232），**不新增第四种外壳**；主面只用一个 surface，内部用分节。
- **入口**：
  1. **rail 底部、「说明」上方「小A同学」+ `⌘⇧A`**：全局助手，所有项目 / 需求共用（详见 §7.8）；
  2. 项目页（`Projects`）页头动作「需求」+ 项目行 `RowMenu` 里的「需求」；
  3. 命令面板「打开需求」「打开助手」；
  4. 从需求派活回来的任务页「上游需求」深链。
- **需求页不占 rail**：需求是项目内的页面；**全局助手占 rail 底部「说明」上方**（`助手 / 说明 / 设置`），因为它是全局对象，不是某个项目的页面。除助手外不再新增 rail 项。
- 页头：`PageHeader` 标题「需求」，副标题一句（`按项目维护需求链，层级可裁剪`）；`actions` = 项目选择器（`select`）+ 一个 primary「新建需求」+ `RowMenu`（裁剪与字段 / 导出 / 数据自检）。
- **项目选择器放页头**：看板 / 计划 / 矩阵都不带左栏，作用域必须跨 tab 保持；换项目 = 换整棵树 / 整块板。
- 页面级切换只用 `Tabs`：**需求池 / 看板 / 计划 / 追溯矩阵**。计数不进 tab。
  - M0 只上「需求池 + 追溯矩阵」；看板 M2、计划 M3，**同页加 tab，不新增页面、不新增 rail 项**。未上线的 tab 不渲染（不做灰色占位）。
  - 「需求池」内部如果需要「树 / 列表」再切，用 `Segmented`（视图切换），不占页面 tab。
- 概览条（`.overview`，≤5 项）：`需求 24 · 已批准 12 · 待评审 3 · 未覆盖 2 · 未验收 5`；`0` 不渲染。

### 7.2 布局

```text

副标题      按项目维护需求链，层级可裁剪

│   ▾ IR-01 范围：只读…    │ 正文（Markdown 阅读 / 双击编辑）        │

```

- 左栏：搜索独占一行 → 层级 / 状态筛选（现有 `select` 模式）→ 需求树。树行 = 行尾 chevron + 状态点 + key（11px `--faint`）+ 标题；行尾：交付层已派活时是 bot 头像（最多 2 个 + `+N`），有缺口 / 待复核再补一个字 chip。
- **看板 / 计划 / 矩阵不带左栏**：切过去后整页给板 / 时间轴 / 表，项目作用域靠页头选择器保持；详情统一用右侧抽屉。
- **列表稳定性**：默认按项目序号固定排序；点击只选中，**不改顺序 / 不改展开 / 不滚动**；展开只由行尾 chevron 触发；「最近更新」只能是用户显式选择的排序。
- 主面：上游链路 → 标题行 → 元信息行 → 按层字段 → 正文 → 验收 → 分节（子需求 / 关联 / 任务 / 时间线）。不叠卡片，不做右栏三列（窄屏会挤）；矩阵 / 看板 / 计划各自独立 tab，**不带左栏**。
- **详情只有一份组件，两种宿主**：需求池里放主面；看板 / 计划 / 矩阵里点卡片或 chip 时，从右侧开 **float 抽屉（宽 460）**，不切 tab、不丢滚动位置。
- **需求会话**是详情标题行的「对话」打开的右侧栏（360），与详情并列；它跟着当前选中的需求切换，默认收起。
- **详情骨架一套，字段按层换**：RR 显示来源 / 提出人；IR 显示范围 / 范围外；SR 显示 EARS 验收 / 影响模块；US 显示角色 / 价值 / Given-When-Then / 估算。不做四套详情页。

**「实现者」在各处的显示（同一份数据，不复制）**

| 位置 | 显示 | 交互 |
|---|---|---|
| 详情元信息行 | `实现 [头像] 小B · 2 个任务`；父级显示 `小B / 小C（来自 3 条子需求）` | 点开跳「任务」分节；交付层多一个 `派活` |
| 需求树行尾 | 交付层且已派活时，14px bot 头像（最多 2 个 + `+N`） | `title` / `aria-label` 写「小B · 2 个任务」；父级不挂头像 |
| 看板卡片 | 底部头像 + 名字 + `1/2 任务`；未派活显示灰色「未派活」 | 板头「实现者」筛选（Bot / 未派活 / 手动任务） |
| 甘特左列 | 行头像 + 名字；逾期/停用用小字标注 | 计划 tab 的「实现者」筛选 |
| 矩阵 | **不显示头像**（格子太窄） | 点 chip 进右侧详情抽屉看 |
| Bot 页 | 每个 bot 行尾「负责需求 3」（`>0` 才渲染），点开为需求列表 | 反向闭环：从 bot 看它接了哪些需求 |

### 7.4 新建、详情与会话入口

- **新建**：页头 primary → 左栏树顶部出现一行行内输入（层级 `select` + 标题），父项默认取当前选中项的下一个启用层，无选中则建 RR；`Enter` 创建并打开详情，`Esc` 取消。正文 / 验收在详情里填，不弹模态框。

- **条件入口**：验收为空且需求还是 draft 时，验收区出现「问助手补一条」；点了只是往同一个会话发一句话，不另开面板。

- **质量检查**：会话里的只读结果卡（阻塞 / 建议 / 通过），不弹模态框，也不在验收区另铺一套列表；`一键修` 不提供。
- **详情元信息行**分开显示「助手 小A同学」与「实现 小B / 小C」：助手不进入实现者聚合。

- **两个 scope**：助手主页不绑定需求（跨项目汇总 / 用法问答）；需求 thread 绑定当前需求（补验收 / 派活 / 看进度）。顶部始终显示当前项目 / 需求上下文，跨项目操作在卡上再标一次项目。

- **六类卡 + 用法卡**：
  - **需求提案**（验收 / 正文 / 下游草稿）：勾选 → 应用，只写 draft；
  - **派活计划**：任务 / 执行 Bot / 工作区 / 是否开跑；点「批准并派活」才建任务、才开跑；
  - **任务进度**：只读，列出任务、Bot、状态、run 链接；可以追问或发起改派；
  - **停 run 提案**：只对 `running / waiting_input` 的 run 出现，带任务、Bot、已运行时长、原因；人批准后停；
  - **关闭提案**：先列 `deliver` / 验收 / `verify` 的完成情况；缺一项就不给关；**即使有授权也要人确认**；
  - **检查结果**：只读，阻塞 / 建议 / 通过；
  - **用法卡**：步骤 + 「带我去」；只读导航，点按钮真的切到需求池 / 看板 / 矩阵 / 裁剪，并在目标控件上闪烁高亮，不写数据；
  - **首页概览卡**：跨项目计数 + 需求池 / 看板 / 矩阵 / 裁剪的「带我去」；
  - **查询结果卡**：「哪些没派活」「哪些验收没过」「哪里断链」；点一条直接选中需求、切到详情、滚到对应区域并高亮（派活按钮 / 验收输入 / 子需求）。
- **授权**：默认每一步都问。计划卡底部可勾「本会话内自动派活」；会话头显示「已授权 · 本会话派活」+「撤销」。项目级长期授权在设置 → 小A同学，覆盖派活 / 开跑 / 改派 / 停 run，带 Bot 白名单 / 每日任务上限 / 并发上限 / 工作区 / 工作时间；**批准需求、关需求永远不授权**。
- **停 run / 关需求**：先读任务 / run 再提；停 run 只在运行中出现，关需求只在交付完成 + 验收全勾 + verify 完成或豁免时出现；缺什么就列什么，不能硬关。
- **权限**：助手可读所有项目 / 需求 / 任务 / run / Bot 状态 / Guide；可写 draft、任务、派活 / 改派、停 run（都在人批准或授权范围内）；不能 approve 需求、改已批准正文、自动关需求。预算与 turn 上限沿用 Bot 档案，每轮进 `bot_turn` 审计。
- **助手从哪来**：`settings.assistantBotId` 指向唯一全局助手；不按项目 / 需求配置。Bot 页的机器人档案里能看到它的「会话 / 负责需求」；换助手只影响后续指挥，不改已派任务。
- **数据**：`threads` 增加 `requirement_id` + `kind='assistant'`，`bot_id` = 全局助手，消息仍走 `messages`；提案与派活计划作为 tool result 落库，应用动作与手工编辑走**同一套 actions**（不新增第二套写路径）。
- **全局**：现有 Chat 里可以 `@CMH-US-07` 打开同一条需求 thread；`⌘⇧K` quick-capture 增加「交给助手」目标，捕获后仍是 draft。
- **不做的**：独立的 AI 表单面板、四种模式、目标字段勾选、提示词表单；按项目 / 按需求配助手；看板卡片 / 甘特条 / 矩阵格子上放助手头像。

### 7.10 可访问性

- 树 `role="tree"` / `treeitem` + `aria-expanded`、`aria-level`；选中态 `aria-selected`。
- 所有纯图标按钮带 `title` + `aria-label`；Tabs 沿用现有 `Tabs` 的键盘行为。
- 矩阵表用真实 `table` + `th scope`；缺口不能只靠颜色，文本要有「缺 / 豁免」。

## 8. 数据与接口

### 8.1 表（与 `electron/db.mjs` 的写法一致）

```sql
CREATE TABLE IF NOT EXISTS requirements (
  id TEXT PRIMARY KEY, project_id TEXT NOT NULL, key TEXT NOT NULL,
  level TEXT NOT NULL, parent_id TEXT, title TEXT NOT NULL, body TEXT DEFAULT '',
  status TEXT DEFAULT 'draft', priority TEXT DEFAULT 'P2', owner TEXT DEFAULT '',
  source TEXT DEFAULT '', acceptance TEXT DEFAULT '[]', tags TEXT DEFAULT '[]',
  meta TEXT DEFAULT '{}', seq INTEGER DEFAULT 0, ai_source TEXT,
  plan_start INTEGER, plan_end INTEGER,                 -- M3 甘特；空 = 未排期
  approved_at INTEGER, approved_by TEXT, deleted_at INTEGER,
  created_at INTEGER, updated_at INTEGER
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_req_key ON requirements(key);
CREATE INDEX IF NOT EXISTS idx_req_project ON requirements(project_id, level, status);
CREATE INDEX IF NOT EXISTS idx_req_parent ON requirements(parent_id);

CREATE TABLE IF NOT EXISTS requirement_links (            -- 只放横向关系，父子用 parent_id
  id TEXT PRIMARY KEY, from_id TEXT NOT NULL, to_id TEXT NOT NULL,
  kind TEXT DEFAULT 'relates',                            -- relates | duplicates | conflicts | depends_on
  created_at INTEGER
);
CREATE TABLE IF NOT EXISTS requirement_tasks (
  id TEXT PRIMARY KEY, requirement_id TEXT NOT NULL, todo_id TEXT NOT NULL,
  kind TEXT DEFAULT 'deliver',                            -- deliver | verify（bot 从 todos.bot_id 派生，本表不复制）
  created_at INTEGER
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_req_task ON requirement_tasks(requirement_id, todo_id, kind);

CREATE TABLE IF NOT EXISTS requirement_revisions (
  id TEXT PRIMARY KEY, requirement_id TEXT NOT NULL, at INTEGER NOT NULL,
  by TEXT DEFAULT 'owner', data TEXT NOT NULL             -- 字段 + 正文快照
);
CREATE TABLE IF NOT EXISTS requirement_profiles (
  project_id TEXT PRIMARY KEY, template TEXT DEFAULT 'standard',
  levels TEXT DEFAULT '["rr","ir","sr","us"]', gates TEXT DEFAULT '{}',
  updated_at INTEGER
);
-- 授权：默认无；人授予后可自动派活 / 开跑 / 改派 / 停 run；关需求永不授权
-- bot_id 固定是全局助手；project_id 空 = 全局授权，有 = 本项目范围
CREATE TABLE IF NOT EXISTS requirement_mandates (
  id TEXT PRIMARY KEY, project_id TEXT, bot_id TEXT,
  scopes TEXT DEFAULT '{}',                             -- {dispatch,start_run,reassign,stop_run}
  constraints TEXT DEFAULT '{}',                        -- {bots,maxTasksPerDay,maxConcurrent,workspace,hours}
  granted_by TEXT, granted_at INTEGER, revoked_at INTEGER
);
CREATE TABLE IF NOT EXISTS requirement_baselines (
  id TEXT PRIMARY KEY, project_id TEXT, name TEXT,
  snapshot TEXT NOT NULL, created_at INTEGER, created_by TEXT
);
```

- `settings` 增加 `assistantBotId`，指向**唯一的全局助手**；不按项目 / 需求配置。
- `threads` 增加 `requirement_id` 与 `kind='assistant'`；`bot_id` 都是这个全局助手，`project_id / requirement_id` 表示 scope：空 = 助手主页，有 = 项目 / 需求 thread。
- 全部走显式列名（老库 `ALTER` 追加列不会错位）。
- `key` 唯一索引兜底；生成序号在写事务里取 `MAX(seq)+1`。
- 软删除：`deleted_at`；已进入 `started / done / closed` 的需求只能 `obsolete`，只有草稿能真删。

### 8.2 State 与增量

- **进 State**：`requirementProfiles`（很小）、`requirements` 的**轻索引**（id / projectId / key / level / parentId / title / status / priority / owner / source / tags / aiSource / updatedAt）、`requirementStats`（每项目各状态计数，供概览条）。
- **不进 State**：正文、验收明细、链接、任务链接、历史、矩阵。按需读。
- **写路径**：需求表**不进 `writeNow()` 的整库 DELETE+INSERT 列表**，改用行级写（`INSERT OR REPLACE` / `UPDATE`），和 `bot_ui` / `saveBotTurn` 同一模式；否则每次改一个状态都会重写全部正文。
- 启动时从 DB 重新加载轻索引；`broadcast()` 仍发全量快照，但需求正文不在其中。
- 保护线：单项目轻索引 > 2000 条时，改为「只发当前项目 + 打开项目时按需拉」，在设置里可看到计数。

### 8.3 IPC 与 actions

读（一个 scoped 频道，避免新增 8 个频道）：

```text
harness:requirements  { op: "get" | "list" | "matrix" | "revisions" | "stats" | "impact", ... }
```

- `get`：一条需求全量（正文 / 验收 / 子项 / 关联 / 任务 / 最近 20 条 revision）
- `list`：按 `projectId / level / status / query / page` 分页（轻字段）
- `matrix`：矩阵行 + 缺口计数（主进程算，返回已聚合结果）
- `revisions`：单条历史；`impact`：递归影响面

写（走现有 `harness:action`）：

```text
requirementProfileSave   requirementCreate      requirementUpdate
requirementSetStatus     requirementMove        requirementLink / Unlink
requirementTaskLink      requirementDelete      requirementRestore
requirementPromoteTodo   requirementImport      requirementExport
requirementDispatch      requirementReassign    requirementStopRun
requirementClose         requirementCheck       requirementBaselineCreate
assistantChat            assistantSetBot
requirementMandateGrant  requirementMandateRevoke
```

- 每个 action 都校验：项目存在、层级启用、父子顺序、状态闸门、父节点未删除。
- 失败返回结构化 `{ error, missing?: string[] }`，界面据此聚焦字段，不靠字符串猜。
- `requirementPromoteTodo` 内部复用 `createTodo` + 写 `requirement_tasks(deliver)`，返回新任务与会话。
- `assistantChat({ projectId?, requirementId? })`：取回 / 创建全局助手的主页或需求 thread；消息走现有 bot turn。
- `assistantSetBot({ botId })`：设置唯一的全局助手；不自动改已派任务。
- `requirementDispatch({ requirementId, items, mandateId? })`：按派活计划批量建任务；只有人点「批准并派活」或落在有效授权范围内才执行。
- `requirementReassign({ taskId, botId })`：只改 `todos.botId` + 时间线，不新建任务。
- `requirementStopRun({ taskId, reason })`：只在 run 处于 running / waiting_input 时可用。
- `requirementClose({ requirementId })`：先校验 deliver 全完成 + 验收全勾 + verify 完成或豁免；缺一项返回 `missing`，即使有授权也要人确认。
- `requirementMandateGrant / Revoke`：人授予 / 撤销授权，写审计；`projectId` 空 = 全局授权。
- 每次写后更新轻索引、写 revision（已批准或状态变化时）、`broadcast()`。

### 8.4 失败语义

| 场景 | 行为 |
|---|---|
| 父节点被裁掉 / 不存在 | 拒绝保存，提示最近的合法祖先 |
| 移动成环 / 同层父子 | 拒绝，提示合法目标层 |
| 状态闸门不满足 | 不写状态；返回 `missing`，界面聚焦缺失字段 |
| 关层迁移失败 | 整批回滚，profile 不变 |
| AI 输出不是合法 JSON / schema 不符 | 不落任何一条，原样保留输出供复制，报错卡可重试 |
| 需求表写入失败 | 内存索引回滚，报错卡；下次重试 |

## 10. 明确不做

- 权限 / 多租户 / 审批人角色体系（单人工作台，`owner` 只是文本）
- 自定义字段引擎、JQL、工作流设计器、状态目录后台
- 关键路径、资源平衡、工时、容量规划（甘特只表达计划与依赖）
- 看板泳道 / 自定义列 / 列内手动排序（列固定 6 个，拖卡只改状态）
- 测试用例管理（验收判据不等于用例；要连外部用例走链接字段）
- 需求评审会议 / 会议室 / 投票
- Jira / OneFlow 双向同步（M3 只做导入与导入预览）
- 实时多人协同编辑（Markdown 冲突用 revision + 乐观锁，不做 OT / CRDT）
- 自动把需求 `done`：验收必须是人的动作
- 需求级的 `assignedBotId` / 主责 bot 字段，或第二套「直接派给 bot」的派单入口
- 独立的 AI 表单面板 / 四种模式 / 目标字段勾选；需求 AI 一律走需求助手会话的提案卡
- 无授权的自动派活 / 开跑 / 改派 / 停 run；自动关需求（关需求永远人确认）
- 按项目 / 按需求配助手；全局只有一个助手，所有项目共用

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 双事实源：repo 里的 `specs/` 与数据库谁算数 | 数据库算数，`specs/` 是单向导出的快照；界面标明导出时间与 commit |
| 裁剪导致追溯断链 | 父节点必须指向启用层，保存即校验；关层走预览 + 整批迁移 + 撤销 |
| 需求数量膨胀，全量广播变慢 | 轻索引 + 正文按需 + 单项目 >2000 条降级为按项目拉取 |
| 又一个「用了两周就空」的看板 / 甘特 | 看板只放交付层且列不可配；甘特没日期就不画条；闸门可豁免但必须留理由；概览只显示「需要你处理」的信号 |
| 实现者与任务漂移 | 不存需求级 bot 字段，实现者只从 `deliver` 任务聚合；改派只改任务；停用 bot 保留历史 |
| 多 bot 归属不清 | 不做单一「主责」，头像叠放 + 任务明细；助手拆解显示「助手 → 子任务」链 |
| 与 Todo 职责重叠 | 需求不做执行状态、不开 run；任务不承载验收判据；两边只通过链接表对话 |
| 助手入口太深 / 又造一套聊天 | 主入口是 rail「小A同学」+ `⌘⇧A`；需求详情「问小A同学」是上下文入口；复用 Chat 组件；提案卡承担结构化，不再做模式面板 |
| 全局助手越权 | 助手只读需求 / 任务 / run；所有写入走提案卡 + 人批准或有效授权；授权有范围 / 约束 / 撤销 / 审计；不能 approve / 关需求 |
| 授权范围失控 | 授权只覆盖派活 / 开跑 / 改派 / 停 run；带 Bot 白名单、每日任务上限、并发上限、工作区、工作时间；一次撤销即失效 |
| 助手与实现者混淆 | 详情元信息行分开显示「助手」与「实现」；助手不挂 deliver 任务，不计入实现者；换助手不自动改已派任务 |
| UI 复杂度失控 | M0 只两个 tab；看板 M2、计划 M3 逐个加，每次加完先删一个多余入口；不新增页面 / rail 项 |

## 12. 需要你确认的决策

1. **入口**：项目页 + 命令面板（推荐，符合 rail 规则）还是 rail 新增「需求」？
2. **裁剪粒度**：项目级（推荐）还是允许单条需求自由跳层？
3. **要不要 IR**：很多团队实际是 RR → SR → US；标准模板是否默认三层的 RR → SR → US？
4. **与 `docs/product` 的关系**：只导出 / 导入（推荐），还是要求双向同步？
5. **US 派活的时机**：M1 就做（推荐，能立刻验证闭环），还是等 AI 拆任务？
6. **评审与基线**：M2 再做（推荐），还是 M0 就要？
7. **助手的粒度**：**整个工作台一个全局助手**（已定），不按项目 / 需求配置。
8. **助手派活的权限**：**默认每次问；人可以授予本会话 / 本项目授权**（已定），随时撤销，授权范围不含批准 / 关需求。
9. **停 run / 关需求**：**先看任务状态**（已定）；停 run 可授权，关需求永远人确认。

确认后：M0 落 `docs/arch/ARCH-requirements.md`（数据结构 / 状态机 / IPC），再按 §9 开工；第一个导入样本用本仓库的 `REQ-bot-chat.md` 做 dogfood。
