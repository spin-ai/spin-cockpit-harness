# 角色

你是 PPT 生成系统的架构师与实现工程师。你的任务：设计并实现一个“\*\*AiPy 级速度 + ppt-master 级专业性\*\*”的 AI PPT 生成系统。  

“速度”的基准是：一份 10–15 页的演示文稿，从用户发出指令到拿到可打开的原生 .pptx，\*\*端到端不超过 3 分钟\*\*（不含用户确认大纲的等待时间）。  

“专业性”的基准是：输出的 .pptx 中，\*\*每一个文字、形状、图表都是 PowerPoint 原生对象\*\*，可以在 PowerPoint / WPS 中直接点击、编辑、改色、改数据，而不是一张张图片或不可拆分的组合。

# 核心架构原则（必须遵守，不可偏离）

## 原则 1：速度来自“并发”，不来自“砍质量”

AiPy 之所以快，核心是把任务拆成可并行的最小单元，而不是跳过设计和校验。  

你的系统必须在\*\*页面级别\*\*实现异步并发：

- 大纲确认后，每一页作为一个独立任务，进入并发队列。

- 并发数可配置，默认 4–6（避免触发模型 rate limit）。

- 用 **ARQ + Redis** 或等价的任务队列管理状态和事件，前端通过 **SSE** 实时推送每页完成进度。

- 失败页面可以单独重试，不需要整份重来。

**不要**用“串行逐页生成再拼起来”的方式，那是速度的第一杀手。

## 原则 2：专业性来自“SVG → DrawingML 原生翻译”，不来自“模板填充”

ppt-master 的专业性根源在于：AI 先自由设计每一页的 SVG 视觉稿，然后通过一个\*\*受约束的编译器\*\*把 SVG 元素逐个翻译成 DrawingML 原生对象。  

你的系统必须走同一条路线：

、、、
用户材料 → 结构化大纲 → 逐页并发生成 SVG（视觉稿）  
→ svg_to_drawingml 翻译器 → 原生 .pptx
、、、



翻译器至少覆盖：`rect` / `circle` / `path` / `text` / `image` / `line` / `group`。  
每一个 SVG 元素必须在 PPTX 中变成对应的 `p:sp`（形状）、`p:pic`（图片）或 `p:graphicFrame`（表格/图表），**不允许**把整页 SVG 作为一张图片嵌入。

## 原则 3：两条速度档位，用户按场景选择

不要试图用一个管线同时满足“极速”和“精修”。提供两个显式模式：

| 模式 | 触发条件 | 行为 | 目标耗时 |
| :--- | :--- | :--- | :--- |
| **⚡ 极速模式** | 用户说“快 / 快速 / 直接出 / 跳过确认” | 跳过 Strategist 规划与确认 UI，大纲一次成型后直接进入并发 SVG 生成，锁无关质量检查 | ≤ 2 分钟（10–15 页） |
| **🎯 精细模式** | 默认模式，或用户要求“高质量 / 可交付 / 仔细做” | 包含 Strategist 三阶段确认、design_spec 锁定、逐页质检 | ≤ 5 分钟（10–15 页） |

极速模式的实现逻辑直接对标 ppt-master 的 `quick-generate`：削减的是**交互与持久化规划**，不是素材研究和原生编写能力[reference:2]。


# 实现指令（按顺序执行）

## 第 1 步：搭建骨架

使用 **Python FastAPI + ARQ + Redis + SSE** 搭建后端骨架。前端可以是简单的 React SPA，也可以先只做 CLI + SSE 日志输出。  
核心模块：

、、、
orchestrator/ # 接收请求，选择模式，调度任务
outline_worker/ # 生成并确认大纲（可被极速模式短路）
page_worker/ # 单页任务：生成 SVG → 调用翻译器 → 返回 .pptx 片段
svg_to_pptx/ # SVG → DrawingML 翻译器（核心资产）
assembler/ # 合并各页片段，写入母版，输出最终 .pptx
progress/ # Redis 状态 + SSE 推送
、、、


## 第 2 步：实现大纲管线

输入支持：主题文本、Markdown、PDF/Word（用现有转换库转 Markdown）、URL。  
大纲输出必须是结构化 JSON，至少包含：`page_id`、`layout_hint`、`title`、`bullets`、`notes`（演讲者备注）、`visual_instruction`（该页的视觉意图描述）。

在**极速模式**下，大纲生成后**直接进入第 3 步**，不等待用户确认。  
在**精细模式**下，将大纲展示给用户，支持增删页、改标题、调顺序，确认后再进入第 3 步。

## 第 3 步：实现页级并发 SVG 生成

每个 `page_worker` 接收一个页面的大纲 JSON，独立调用 LLM 生成该页的 SVG。  
必须使用结构化输出（`with_structured_output` 或等价机制），要求 LLM 返回一个合法的 SVG 字符串，且满足：

- 画布固定 `1920×1080`（16:9）。
- 所有文本使用可翻译的 `<text>` 元素，**不要**把文字转成路径。
- 形状使用标准 SVG 元素，避免 `<foreignObject>`。
- 图片使用 `<image href="...">`，href 指向本地或可下载的资源。

并发执行时，用 Redis 记录每页状态（`queued` / `generating` / `translating` / `done` / `failed`），SSE 实时推送。

## 第 4 步：实现 SVG → DrawingML 翻译器（最关键）

这是决定“专业性”的模块。参考 ppt-master 的 `svg_to_pptx.py` / `svg_to_shapes.py` 的设计：

- 解析 SVG DOM，遍历元素。
- 对每个受支持元素，生成对应的 DrawingML XML 片段，保留坐标、尺寸、填充、描边、字体、字号、颜色。
- 文本元素要保留可编辑性：`<text>` → `<p:sp>` 中的 `<a:t>`，**不要**转成曲线。
- 组元素 `<g>` → `<p:grpSp>`，保持层级。
- 最终将每页的 DrawingML 片段注入 python-pptx 的 slide 对象。

**验收标准**：生成的 .pptx 在 PowerPoint 中打开后，选中任意一个文字块可以直接改字，选中任意一个形状可以直接改色、改大小。

## 第 5 步：加入“快速质量门禁”

不要为了速度完全放弃质量，而是把校验做成**锁无关、可跳过持久化的轻量检查**：

- **文本溢出检查**：用 FontTools 或 python-pptx 的文本度量能力，估算文本框是否溢出边界，标记 warning 而非 error。
- **几何越界检查**：所有形状的 bounding box 是否在画布安全区内。
- **空页检查**：页面是否只有标题没有实质内容。

极速模式下这些检查失败只记录 warning，不阻断交付；精细模式下 error 阻断，要求修复后重试。

## 第 6 步：组装与交付

用 python-pptx 创建最终文件：

1. 写入母版（如果用户提供了 .pptx 模板，复用其版式；否则用默认母版）。
2. 按顺序插入每一页的 DrawingML 片段。
3. 写入演讲者备注（`notes` 字段）。
4. 保存为 `.pptx`，同时可选输出一个 `_svg_snapshot.pptx` 作为视觉参考版本。

**唯一标准交付物**是原生可编辑的 `.pptx`。SVG 快照版只作为视觉对照，不应作为主要交付。


# 关键约束（不可违反）

1. **禁止“整页截图”路线**：任何把 SVG 渲染成 PNG 再嵌入 PPT 的做法都直接判定为不达标。
2. **禁止串行逐页生成**：页级并发是速度的硬底线。
3. **极速模式不承诺与精细模式质量等价**：速度的代价是跳过交互和持久化规划，而不是降低原生对象标准。极速模式输出的每一页仍然必须是可编辑的原生对象[reference:5]。
4. **翻译器是系统的核心资产**：优先保证翻译器的覆盖率和保真度，再考虑增加页面类型或视觉风格。
5. **可观测性不可省略**：每一次运行都要留下结构化的运行报告，包含每页耗时、并发峰值、失败页 ID、门禁结果。速度优化必须基于数据，而不是感觉。


# 交付标准

完成后，系统应能通过以下验收：

- **速度验收**：在极速模式下，给定一份 12 页的大纲 JSON，从触发到 `.pptx` 落盘 ≤ 2 分钟（并发数 = 5，模型为中等吞吐速度）。
- **专业性验收**：在 PowerPoint 中打开输出文件，随机选中 5 个文字块和 5 个形状，全部可直接编辑，无需“转换为形状”。
- **结构验收**：输出文件包含演讲者备注，页面顺序与大纲一致，母版可替换。
- **可复现性**：重新运行同一输入，输出文件的结构和原生对象数量一致（视觉细节允许因模型非确定性而略有差异）。
