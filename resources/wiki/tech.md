# 五个技术难点

> 判断标准不是「接了多少模型」，而是这件事**难在哪**、**做到什么算做到**、**现在到哪了**。依据 `docs/arch/ARCH-key-tech.md`。

## 一句话

| # | 难点 | 类型 | 现在到哪了 |
|---|---|---|---|
| ① | 解析 | 真技术 | 本地直抽 + 页图 + 引擎路由；VLM / OCR 兜底与质量度量未做 |
| ② | 编排 | 工程 | Mission / worktree / 审批 / 终端上报已落地；3 Agent 并行的可见性未验证 |
| ③ | 整理 | 产品 | 建议队列 + 逐行 diff + 人工结论已落地；采纳率还没攒出数据 |
| ④ | 记忆 | 语义设计 | 四层 + 注入台账 + Dream 建议已落地；归因只到标题片段 |
| ⑤ | 画像 | 语义设计 | 导入 / 双时态 / measures / 合并建议已落地；剩下是调优 |

难度排序：**① 解析 > ④ 记忆 ≈ ⑤ 画像 > ② 编排 > ③ 整理**。
① 是唯一「做了但看起来不像做了」的模块，因为没有精度数字；其余四件的效果能直接感知。

## ① 解析：极小资源下的高精度

- **难在哪**：「各类」是无限长尾 —— 双栏、嵌套表、跨页表、公式、手写、页眉页脚，没有单一方法能全覆盖。
- **关键约束**：分层（本地直抽 → 页图 → VLM）+ **每页给置信度**；低置信度必须显式标出，不能假装解析成功。
- **判据**：20 份真实材料，文本覆盖 ≥95%、表格单元格 ≥90%、引用页命中 ≥90%、recall@5 ≥80%。
- **现在**：`unpdf` / `mammoth` / `xlsx` / `officeparser` / `epub2` 直抽、页图渲染、引擎注册与路由（simple / builtin / mineru / paddle / custom）已落地。
- **硬缺口**：VLM / OCR 兜底还是空实现，扫描件现在出空页；解析质量没有任何度量。顺序是「度量脚本 → VLM 兜底 → 表格保结构 → 分块不切断表格」。

详见 [知识库](#/wiki/knowledge)。

## ② 编排：状态可见 + 干预一致

- **难在哪**：不是「能起多个 Agent」，而是**状态能不能一眼看懂**、**干预后不产生半成品**、并发写同一仓库时能回滚。
- **关键设计**：子任务靠 `artifacts` 引用传递，不塞 prompt；审批落库（谁 / 何时 / 哪个入口）；终端**主动上报**，不解析屏幕文本。
- **判据**：3 个 Agent 并行同一项目，不翻终端就能说出「谁卡住」；中断后仓库能回到一致状态。
- **现在**：ACP over stdio、node-pty、Mission / Plan / Delegation、worktree 隔离、审批队列、`todo/claim` 上报都已落地。
- **风险**：Agent 不调上报工具就退化成人工盯屏 —— 这是**行为风险**，靠 prompt + 强制工具，不是加监控能解决。

详见 [Super Agent / Mission](#/wiki/super-agent)、[场景与办公室](#/wiki/office)。

## ③ 整理：正确性无法自动验证

- **难在哪**：合并两页、补引用、标过期，做错比不做更糟；「整理对了没有」没有自动判据。
- **关键设计**：后台只产**建议**，不直接改 `reviewed`；每条建议带 evidence + `baseHash`；提议即产物（批准 = 字节拷贝，不重调模型）；页面已改过 → `needs_rebase`，不自动合并；拒绝也留痕、同类 30 天不重复打扰。
- **判据**：reviewed 页面从不被静默改写（自检断言 = 0）；source 变更后引用页自动 `stale`；建议采纳率 / `needs_rebase` 占比。
- **现在**：`wiki.curate`（确定性、免费秒级）、`suggestions` 建议队列、逐行 diff 审核门、人工结论（claim）、`wikiCurateLLM`（只改摘要 / 要点）已落地。
- **天花板**：自动「写出人能用的页面」很难；「结构整理免费 + 模型只润色摘要」是稳的那一档。

详见 [LLM Wiki](#/wiki/llm-wiki)。

## ④ 记忆：记什么、忘什么

- **难在哪**：记得越多，注入越差。上下文窗口再大也不是记忆；顶层一旦污染会拖累每一次会话。
- **关键设计**：越高层越小；L1 不可写（Dream 的 ground truth）；晋升必须可追溯且人工接受；Dream 可关、有预算。
- **判据**：开 / 关 Dream 的返工次数对比；L4 注入条目被实际引用的比例。
- **现在**：四层 + note + 打分注入 + 注入台账 + L1 bigram 索引 + Dream 建议队列已落地。
- **头号风险**：自动晋升污染每一次会话 —— 所以晋升只能产建议，而且要能回到上一个 `memory_version`。

详见 [记忆与 Dream](#/wiki/memory)。

## ⑤ 画像：推断的可信度

- **难在哪**：规则抽取宁可漏也不乱猜；模型会编，所以一切推断必须先 `pending`。隐含偏好只能靠模型，而模型必然有幻觉 —— 这是**产品问题**（确认成本 vs 画像价值），不是算法问题。
- **关键设计**：没有来源不能确认；群聊 ≠ 亲密；`valid_to` 由确认驱动（两个方向都要处理）；矛盾只在「同时有效」时成立。
- **判据**：确认队列的误报率；`asOf` 回看与当时的对话是否一致。
- **现在**：四格式导入、规则抽取、三层画像、双时态 + `asOf`、群聊降权、候选确认队列、敏感标记、`measures` 与合并建议已落地。

详见 [人物画像与记忆语义](#/wiki/persona)。

## 共同原则

**机器只负责「提出来」，人只负责「点头」，中间每一步都留证据。**

五件事共用一套底座，所以不要按五条独立系统去设计：

```text
本地零依赖运行时（Electron 45 / Node 24 / node:sqlite；无 Docker / Python / 原生编译）
        │
  ┌─────┴─────┬──────────┬──────────┬──────────┐
 解析         编排         整理         记忆         画像
 ①           ②           ③           ④           ⑤
  └───── 一把 Ark key（chat / VLM / embedding）─────┘
  └──── 一套确认语义（内容审核 / 记忆确认 / 晋升）────┘
  └──── 一条出口（MCP 只读工具，per-run 子进程 + token）────┘
```

判断一项新技术值不值得引入，看它是否**同时**满足：能装进 Electron、不新增服务进程、失败时能降级而不是整个模块不可用。

## 明确不做

| 做法 | 原因 |
|---|---|
| 引入 PaddleOCR / RAGFlow 服务 | 要 Python + 服务进程，与「极小资源」冲突 |
| 让 LLM 整篇重写原文 | 贵，且不可引用（无法保证与原文对应） |
| 全量页走 VLM | 每页一次调用；数字原生 PDF 纯属浪费 |
| 追 bbox 级引用定位 | 坐标不稳，页级 + 段级已足够核对 |
| 为记忆 / 画像引入独立向量库 | 个人语料规模下 `node:sqlite` + 暴力 cosine 足够 |
